## 1. [P0·저위험] D17-1 — stuck-sweep cron 단일화 (아키텍처 결정)

### 현 상태 (untracked, 워킹트리)
```
apps/web/app/api/cron/sweep-stuck-jobs/route.ts   ← 자체완결 updateMany, web/vercel.json cron 등록
apps/api/app/cron/sweep-stuck-jobs/route.ts       ← sweepStuckJobs() 호출(수동/유료)
apps/api/app/cron/sweep-stuck-jobs/sweep.ts       ← 로직 헬퍼(정본)
apps/api/app/cron/keep-alive/route.ts:25          ← sweepStuckJobs() 하루1회 합승 호출
```

### 결정 기준 — **어느 앱이 배포되는가**가 유일한 판단축
- www.findable.co.kr = **apps/web** (라이브·env 세팅·cron 실행 가능) [확인사실]
- apps/api = **미배포** [확인필요 — Vercel 프로젝트 존재하나 도메인·cron 실행여부 미확인]

### 안 A (web 단일화 — 배포 현실 우선) ✅ 권장
- **정본 = web**. api쪽 sweep-stuck-jobs 3파일 + keep-alive의 sweep 호출 제거.
- 로직 헬퍼를 `apps/web/lib/audit/sweep-stuck-jobs.ts`로 이동(route.ts는 헬퍼 호출만) → web 안에서 (a) cron route (b) 향후 수동 트리거 재사용.
- 근거: cron은 배포된 앱에서만 돈다. api 미배포면 keep-alive 합승도 안 돎 = **현재 stuck 정리는 web cron만 실효**. api쪽은 죽은 코드.

### 안 B (api 단일화 — 관심사 분리 우선)
- 정본 = api(sweep.ts 헬퍼 + keep-alive 합승). web route 제거, web/vercel.json cron 삭제.
- **전제**: apps/api를 실제 배포+cron 실행하도록 만들어야 함(현재 미배포면 stuck 정리 0). = 배포 작업 선행 필요 → 고위험.

### 권고: **안 A**. 이유 = "지금 실제로 도는 것"을 정본으로. 단, ⚠️ **이 파일들은 오늘 다른 세션이 만든 미커밋 상태** → 그 작업 의도 확인 없이 삭제 금지. 사용자에게 "web/api 중 어느 방향으로 정리했는지" 먼저 확인.

## 2. [P1] D17-5 — 운영자 장애 알림 (로그 → 알림 승격)

### 문제
stuck 잡을 쓸어도 `log.warn("cron.sweep-stuck-jobs.swept", {fast, crew})` 로그만 남음. 아무도 안 봄. **알림이어야 할 것을 로그로 대신**(§0 3축 혼용 함정).

### 명세 — 임계 초과 시에만 능동 통지 (노이즈 방지)
```ts
// sweepStuckJobs() 말미, 로그 다음에:
if (swept.fast + swept.crew >= ALERT_THRESHOLD) {   // 예: 3건 이상 = 이상 신호
  // 1순위(무추가의존): Sentry 메시지 — 이미 붙어있음
  captureMessage(`stuck-sweep: ${swept.fast} fast + ${swept.crew} crew swept`, "warning");
  // 2순위(선택): 슬랙 웹훅 or Resend 운영자 메일. env 없으면 skip(graceful).
}
```
- **원칙**: 정상(0건 스윕)은 조용, 이상(임계 초과)만 통지. Sentry는 이미 연결돼 있어 **추가 의존 0**으로 즉시 가능.
- 임계값·채널은 env로. `SWEEP_ALERT_THRESHOLD`(기본3), `SWEEP_ALERT_SLACK_WEBHOOK`(옵션).

### 검증
- [ ] 스윕 0~2건 = 알림 없음 / 3건 이상 = Sentry warning 1건
- [ ] 슬랙 env 없을 때 크래시 없이 skip

## 5. [P2] D17-4 — Knock in-app 알림 실트리거 (반쪽구현 완성)

- 현재: 피드 UI(provider)만, 넣을 알림 0.
- 후보 트리거: 진단 완료(`audit.completed` → in-app "리포트 준비됨") · crew 심층분석 완료 · 결제 완료.
- ⚠️ apps/app(대시보드)은 로그인 사용자용인데 audit는 apps/web(비로그인) 플로우 → **userId 매핑 필요**. 현 구조상 audit 사용자는 익명(email만) → Knock userId 없음. **선결: audit→계정 연결 모델**(요금제/파트너 승인과 연계). 그래서 P2 최하위.
