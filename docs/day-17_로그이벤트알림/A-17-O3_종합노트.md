# A-17-O3 — 종합 노트 (로그·이벤트·알림)

> Day17 (2026-07-28) · Findable · 3주차 마감 직전

## 오늘 한 일
Findable 실코드를 로그/이벤트/알림 3축으로 블라인드 재검증. next-forge 덕에 3축 인프라(Logtail·Sentry·PostHog·Knock·Resend)는 이미 다 연결돼 있음을 확인 → 오늘의 진짜 발견은 "도구 없음"이 아니라 **정리 안 된 파이프라인과 3축 혼용**.

## ★ 핵심 발견 5건 (→ A-17-O1)
- **D17-1** stuck-sweep cron이 web·api 두 곳 중복 + 둘 다 untracked + 설계 상충(web 별도cron vs api keep-alive합승). **오늘 다른 세션이 구현 중인 미커밋 상태** = Day14~16 "명세만"이 실은 오늘 반영됨(단 미정리).
- **D17-2** 로그 편중: audit 촘촘(`도메인.대상.동작` 구조화 우수) but 인증·결제·브랜드 도메인 무로그.
- **D17-3** 이벤트(PostHog) 실작동하나 클라3+webhook만 → 전환 퍼널 중간 끊김.
- **D17-4** 알림=Knock 연결만·발송 트리거 0(반쪽구현). 실제 사용자 도달 = Resend 이메일 1경로.
- **D17-5** 운영자 장애 알림 부재 — stuck 스윕이 로그에만 남고 아무도 안 봄.

## 핵심 교훈 3가지
1. **로그·이벤트·알림은 목적·수신자·보존이 다르다.** 혼용하면 알림이어야 할 것을 로그로 대신(D17-5)하는 실수가 난다. 관측성은 도구 개수가 아니라 "누가 무엇을 보는가"의 문제.
2. **"명세만 있다"는 판정은 시점 의존적이다.** Day14~16 내내 sweep을 "미반영"으로 적었는데 오늘 보니 구현돼 있었다. 블라인드 재검증을 **매번 실코드로** 다시 하는 규칙이 왜 필요한지 실증(메모리만 믿었으면 이미 있는 걸 또 만들 뻔).
3. **미커밋 워킹트리 = 관측 사각지대.** git이 모르는 코드는 배포·롤백에서 유실되고, 어느 게 최종인지 아무도 모른다. untracked도 "이상 신호"로 봐야 한다.
