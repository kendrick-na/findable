## 0. 오늘의 대상 정의 — 3축

| 축 | 정의 | 교재 통상 도구 | Findable 실측 도구 |
|----|------|----------------|--------------------|
| **로그(Logging)** | 시스템 내부 상태·에러의 시계열 기록. 사후 디버깅·장애 추적용 | pino/winston + Sentry | `@repo/observability` = prod:Logtail·dev:console + `@sentry/nextjs` |
| **이벤트(Events)** | 사용자·비즈니스 행동의 의미 단위 기록. 제품분석·퍼널·전환 측정용 | PostHog/Amplitude | `@repo/analytics` = PostHog(client+node) |
| **알림(Notifications)** | 사람에게 도달하는 능동 통지. in-app 피드 / 이메일 / 슬랙 등 | Knock/Novu + Resend | `@repo/notifications`=Knock · `@repo/email`=Resend |

**핵심 구분(교재 함정)**: 로그·이벤트·알림은 자주 뒤섞여 이해되지만 목적·수신자·보존이 다르다.
- 로그 = 개발자가 본다 · 사후 · 짧게 보존(관측 플랫폼)
- 이벤트 = 분석가/PM이 본다 · 집계 · 장기 보존(분석 DB)
- 알림 = 사용자/운영자가 본다 · 실시간 · 도달이 목적
→ **혼용하면**: 알림을 로그로 대신(사용자가 장애를 모름) / 이벤트를 로그로 대신(퍼널 분석 불가) / 로그를 이벤트로 오염(분석 노이즈). Findable 재검증의 채점축.

## 1. 블라인드 재검증 — 실측 발견 (★ 5건)

### D17-1 [확인사실] stuck-sweep cron이 **web·api 두 곳에 중복 구현 + 둘 다 untracked**
- `apps/web/app/api/cron/sweep-stuck-jobs/route.ts` : 자체 완결(updateMany 직접 2회). **`apps/web/vercel.json` cron 등록됨**(`0 1 * * *`).
- `apps/api/app/cron/sweep-stuck-jobs/{route.ts,sweep.ts}` : 로직을 `sweepStuckJobs()` 헬퍼로 분리. `apps/api/app/cron/keep-alive/route.ts:25`가 **실제로 이 헬퍼를 호출**(하루1회 합승). route.ts는 수동/유료-15분cron 진입점.
- **git status: 두 폴더 다 `??`(untracked)** — 어느 것이 최종본인지 버전관리가 모름. 오늘(7/28 16:38~16:40) 워킹트리에만 생성.
- **모순**: api 주석 "Hobby 하루1회라 keep-alive 합승"(별도 cron 안 씀) vs web은 별도 cron으로 등록. web 주석 "api 미배포라 web에 둠". → **두 설계가 공존**. 배포앱은 web(www.findable.co.kr 라이브), api는 미배포[확인필요].
- **위험**: 둘 다 살아 있으면 (a) 중복 실행 (멱등이라 데이터 안전하나 로그·함수비용 이중) (b) 미커밋이라 배포·롤백 시 유실. Day14~16 내내 "명세만·미반영"이라던 것이 실은 **오늘 구현됐으나 정리 안 된 상태**.

### D17-2 [확인사실] 로깅은 **audit 도메인에 촘촘, 나머지 도메인은 공백**
- log 호출 파일: audit route 6종 + audit runner 3종 + cron 2종 + webhook 2종 = **audit·webhook·cron에 집중**.
- 이벤트 네이밍 규율 우수: `audit.job.created` / `audit.crew.stale_restart` / `lead.email_sent` = **`도메인.대상.동작` 구조화 키** (grep으로 특정 이벤트 추적 가능).
- **공백**: 인증(Clerk 로그인/가입 플로우 자체)·브랜드 등록/담당자 배정(Day07·10 슬라이스)·결제 체크아웃(PortOne 성공/실패) 도메인엔 구조화 로그 없음. webhook은 있으나 앱 내 액션 경로는 무로그.

### D17-3 [확인사실] 이벤트(PostHog)는 실작동하나 **클라 3종·서버 webhook만**
- 클라: `audit_started` · `lead_submitted` · `share_kakao_clicked` (`audit-result.tsx`).
- 서버: webhook auth/payments에서 `analytics?.capture(...)` 다수(가입·결제 등).
- **퍼널 공백**: 핵심 전환 경로 중 "진단완료→리포트조회→가격조회→체크아웃" 중간 단계 이벤트 부재 → **AARRR Activation/Revenue 퍼널이 끊김**. 지불의사 검증(P0)의 계측 근거가 약함.

### D17-4 [확인사실] 알림 = Knock **연결만, 발송 트리거 0** (반쪽구현, D12·D13 계열)
- `@repo/notifications` = `new Knock(key)` 정의 + `NotificationsProvider`가 `apps/app` sidebar에 마운트(in-app 피드 UI 존재).
- 그러나 `notifications.workflows.trigger(...)` 같은 **실제 발송 호출은 코드 전체에 0건**[확인필요, grep 미검출]. → 피드 UI는 있는데 넣을 알림이 없음.
- **유일하게 도달하는 알림 = 이메일**: `lead` route에서 Resend로 리포트 발송(`lead.email_sent` 로그로 확인). = 알림 축에서 실제 사용자 도달은 이메일 1경로뿐.

### D17-5 [확인사실] 운영자 알림(장애 통지) 부재
- stuck-sweep가 잡을 죽인 잡을 `log.warn("cron.sweep-stuck-jobs.swept")`로 **로그만** 남김. 운영자에게 능동 통지 없음.
- Sentry가 예외는 캡처하나(에러), "잡이 stuck돼서 쓸어냄" 같은 **비-예외 이상 신호**는 로그에만 있어 아무도 안 봄 → D17 3축 혼용 함정(§0)의 실제 사례: **알림이어야 할 것을 로그로 대신**.

## 3. 판단 — 오늘 가장 가치 있는 개입

**Day17의 진짜 gap은 "관측 도구 도입"이 아니다.** 3축 인프라(Logtail·PostHog·Knock·Resend·Sentry)는 이미 next-forge로 다 붙어 있다. 진짜 문제는:

1. **정리 안 된 stuck-sweep 이중구현(D17-1)** — 오늘 발생한 실재 혼선. 관측 파이프라인의 신뢰성을 직접 해친다(어느 cron이 도는지 불명확).
2. **운영자 장애 알림 부재(D17-5)** — stuck 잡이 쓸려도 아무도 모름. Day13~16 내내 다룬 crew stuck 문제의 "사후 가시성"이 로그에만 갇힘.

→ **우선순위**: D17-1(sweep 단일화 결정) = P0 저위험(문서 결정+코드 정리), D17-5(운영자 알림) = P1. 나머지(로깅 도메인 확장·퍼널 이벤트·Knock 트리거)는 P2 백로그.

**⚠️ 실코드 반영은 §7.3(라이브 서비스) 규칙에 따라 사용자 확인 후.** 특히 D17-1은 **오늘 다른 세션 작업이 진행 중인 미커밋 상태**라, 그 작업의 의도를 확인하지 않고 건드리면 충돌. 이번 산출물은 **재검증·명세·결정안 제시**까지.
