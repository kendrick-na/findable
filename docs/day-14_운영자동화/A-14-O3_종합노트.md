## 1. 한 줄 요약

Findable엔 운영 자동화가 **keep-alive(DB 보온) 하나뿐**이고 관리자 콘솔(`apps/studio`)은 **빈 껍데기**였다. 즉 서비스가 돌면 운영자가 "멈춘 job·실패·리드"를 볼 데도 자동 정리할 장치도 없다. 다행히 자동화의 재료(AuditJob 상태 필드·인덱스)는 이미 완비돼 있어서, 어제(Day13) 미룬 crew stuck P0를 **cron 스윕으로 승격**하는 게 Day14의 정답으로 딱 맞아떨어졌다.

## 2. 오늘의 핵심 발견 (블라인드 재검증)

| # | 발견 | 확신도 | 처리 |
|---|------|--------|------|
| **D14-1** | 운영 자동화 = keep-alive(보온) 1개뿐, 비즈니스 자동화 0. Day04 자동화 후보 3건 전부 미구현 | [확인사실] | stuck 스윕·집계 cron(P0/P1) |
| **D14-2** | 관리자 콘솔(apps/studio) 빈 껍데기(소스 0). 운영 가시성 0 | [확인사실] | 콘솔 최소판(P1) |
| **D14-3** | 자동화 재료(status·crewStatus·createdAt·index)는 이미 완비 → 스키마 무변경 저위험 | [확인사실] | 즉시 착수 가능 |
| **D14-4** | Day13 crew stuck P0 = Day14 cron 스윕으로 승격이 정답(조회 판정 → 자동 정리) | [AI가설] | Day13·14 P0 통합 |

> Day12·13은 "재료가 없거나(모델·가드 부재)" 문제였는데, **Day14는 재료가 다 있고 안 쓰는** 문제. 그래서 확신도 높고 저위험. 실제로 손대기 가장 쉬운 Day.

## 3. Day13 → Day14 연결 (누적되는 주제)

- Day13: crew가 `after()` 크래시 시 `crewStatus="processing"` 영구 stuck → "조회 시 stale 감지"를 P0로 등록.
- Day14: 그 stale 감지를 **사용자 조회에 의존하지 말고 cron이 주기적으로 스윕**하자로 승격. audit `status`도 같은 방식으로 함께 정리.
- → 두 Day의 P0가 하나의 cron(`sweep-stuck-jobs`)으로 합쳐짐. **자기개선(Day13)이 운영 자동화(Day14)로 자연스럽게 이어짐.**

## 4. 자동화 & 콘솔은 세트라는 교훈

- cron으로 뭘 자동 정리해도 **결과를 볼 콘솔이 없으면 "조용히 돌기만" 함** → 문제가 생겨도 모름.
- 그래서 Day14는 "자동화(cron)" + "가시성(콘솔)"을 한 세트로 설계. 집계 cron의 결과가 콘솔에 뜨고, 콘솔에서 stuck을 눈으로도 확인.
- ⚠️ **콘솔의 역설**: 일반 앱은 org 스코핑으로 데이터를 "가두는" 게 정답인데(Day11), 관리자 콘솔은 크로스-org 조회가 정당하되 **admin 역할로 게이트**. 방향이 반대라 헷갈리면 최대 위험(일반 사용자가 전사 데이터 봄). Day11 스코핑과 나란히 기억.

## 5. Findable 실행 순서 (§7.3 확신도 차등)

1. **P0 stuck 스윕 cron** — Day13+14 P0 통합. 스키마 무변경, keep-alive 인증 패턴 재사용. 가장 먼저.
2. **P1 운영 집계 cron** — 읽기 집계, 부작용 없음.
3. **P1 콘솔 최소판** — apps/studio 채우기. admin 역할 게이트 선결.
4. **🟡 콘솔 쓰기(수동 재처리)** — 감사로그 필요, 나중.
