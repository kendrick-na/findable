## 0. 오늘의 대상 = Findable의 운영 자동화 & 관리 콘솔

커리큘럼 Day14 = "운영 자동화·관리자 콘솔 만들기". 실습 규칙대로 새로 만들지 않고, **Findable에 이미 있는 것부터 실측**한다.

### 실측 파일 (2026-07-23 확인)
| 대상 | 실측 결과 |
|------|----------|
| cron (운영 자동화) | `apps/api/app/cron/keep-alive/route.ts` **1개뿐** |
| cron 스케줄 | `apps/api/vercel.json` → `/cron/keep-alive` 매일 `0 1 * * *`(새벽 1시) |

## 1. 현재 상태 [확인사실]

### 1-1. keep-alive cron
```
GET /cron/keep-alive
  → CRON_SECRET 또는 x-vercel-cron 헤더로 인증
  → database.page.create({ name: "cron-temp" }) 후 즉시 delete
  → "OK" 200
```
- **목적: Neon 콜드스타트 방지**(DB를 매일 한 번 깨워 첫 요청 지연 회피). 더미 write/delete.
- 즉 **비즈니스 운영 자동화가 아니라 인프라 보온용**. 실제 "운영"을 자동화하는 건 아직 없음.

### 1-2. 관리자 콘솔 = 빈 껍데기
- `apps/studio`에 라우트·컴포넌트·페이지가 하나도 없음(package.json + tsconfig만).
- Day01 진단의 "studio 타입오류 1"도 이 빈 앱에서 나온 것.
- → **관리자가 audit/lead/crew 현황을 볼 화면이 지금은 없음.** 운영자가 DB를 직접 쿼리하거나 Vercel 로그를 봐야 함.

## 2. "무엇을 자동화·관리해야 하는가"를 새로 도출 (블라인드)

Findable이 실제로 돌아가면 운영자가 매일 신경 써야 할 것:

| 운영 질문 | 지금 어떻게 답하나 | 자동화/콘솔 필요성 |
|-----------|-------------------|-------------------|
| 오늘 audit 몇 건 돌았나? 성공률은? | 수동 DB 쿼리 | 콘솔 대시보드 |
| **멈춘(stuck) job 있나?** (Day13 발견) | 아무도 모름 | **자동 감지 cron** |
| 실패한 audit 재처리했나? | 수동 | 자동 재시도 |
| 새 리드(Lead) 들어왔나? | 수동 | 알림 자동화(Day17) |
| crew가 processing에 박혀있나? | 아무도 모름 | **stuck 스윕 cron** |
| 어뷰즈(같은 IP 폭주) 있나? | ipAddress 필드만 있음 | 집계 콘솔 |

→ **가장 급한 자동화 = "멈춘 job 감지·정리"**. 이건 Day13에서 이미 발견한 P0(`after()` 크래시 시 crewStatus="processing" 영구 stuck)와 **정확히 같은 문제**. Day14는 그걸 "cron으로 자동 감시"하는 형태로 승격.

## 3. 현재와 대조 = 발견 (★핵심)

### D14-1 [확인사실] **운영 자동화가 "보온(keep-alive)" 하나뿐 — 비즈니스 자동화 0**
- 있는 cron은 DB 콜드스타트 방지용 더미. audit 파이프라인·리드·crew 어디에도 자동 감시/재처리/집계가 없음.
- Day04에서 "자동화 후보 3(AuditJob 상태전이·진단 파이프라인·주간 SoV 배치)"을 설계했으나 **실제 cron으로 구현된 건 0개**.
- **함의**: 운영은 전부 수동. 서비스가 커지면 "멈춘 job·실패·어뷰즈"를 사람이 눈으로 못 따라감.

### D14-2 [확인사실] **관리자 콘솔(apps/studio)이 빈 껍데기 — 운영 가시성 0**
- 소스 0개. 운영자가 "지금 무슨 일이 일어나는지" 볼 화면이 없음.
- next-forge가 studio 앱 슬롯을 제공했지만 Findable은 채우지 않음.
- **함의**: 자동화(cron)로 뭘 하든 그 결과를 **볼 데가 없음**. 자동화와 콘솔은 세트.

### D14-3 [확인사실] **자동화의 재료(스키마)는 이미 완비됨**
- AuditJob에 `status`(queued/processing/completed/failed)·`crewStatus`·`createdAt`·`completedAt` + `@@index([status])`·`@@index([createdAt])`.
- → **stuck 감지·집계·재처리 cron이 스키마 변경 없이 즉시 가능**. Day12(모델 없음)·Day13(가드 없음)과 달리 여기선 재료가 다 있음.
- 즉 Day14는 "새 인프라"가 아니라 "이미 있는 상태 필드를 cron이 읽기만 하면 되는" 저위험 자동화.

### D14-4 [AI가설] **Day13 crew stuck P0 = Day14 자동화로 승격이 정답**
- Day13에서 "crewStartedAt 15분 초과 + processing = stale 감지"를 P0로 등록했는데, 이걸 조회 시점 판정이 아니라 **cron 스윕**으로 돌리면 사용자가 안 봐도 자동 정리됨.
- audit `status`도 동일(queued/processing에 오래 박힌 것 = stuck).
- → Day13 P0와 Day14 자동화가 하나로 합쳐짐. [확인필요]: Vercel cron 최소 주기(무료 플랜 하루 1회 제한?) 실측.

## 4. 설계 제안 — 운영 자동화 & 콘솔 (미확정, §7.3)

### 4-A. stuck job 스윕 cron (P0 — Day13 P0 승격, 저위험)
```
GET /cron/sweep-stuck-jobs   (매시간 또는 Vercel 최소주기)
  1. audit: status IN (queued, processing) AND createdAt < now-15min
       → status=failed, errorMessage="STUCK: swept by cron" 로 정리
  2. crew: crewStatus=processing AND crewStartedAt < now-15min
       → crewStatus=failed, crewCompletedAt=now
  3. 정리 건수 log.info (관측)
```
- 스키마 변경 없음. 기존 상태 필드 UPDATE만. Day13 명세(A-13-O2 §3)와 동일 로직을 cron화.

### 4-B. 운영 집계 cron (P1)
```
GET /cron/daily-ops-digest   (매일 1회)
  - 어제 audit 총건/성공/실패/평균 소요, crew 요청/완료율, 신규 Lead 수 집계
  - 결과를 log 또는 (Day17) 이메일/슬랙 알림
```

### 4-C. 관리자 콘솔 최소판 (P1 — apps/studio 채우기)
- 읽기 전용 대시보드 1페이지: 오늘/7일 audit 현황, stuck 목록, 최근 Lead, crew 상태 분포.
- ⚠️ **org 스코핑 불필요? [확인필요]** — 관리자 콘솔은 전사 데이터를 보므로 Clerk **admin 역할** 게이트 필요(일반 org 스코핑과 반대: 여기선 크로스-org 조회가 정당하되 admin만). Day11 org 스코핑과 방향이 다름 = 주의.
- 최소판은 조회만. 수동 재처리 버튼 등 쓰기는 다음 단계.

### 4-D. Day04 자동화 후보 3건 회수
- Day04 A-04-O3에서 설계한 ①AuditJob 상태전이 ②진단 파이프라인 ③주간 SoV 배치 → 지금까지 미구현. 4-A/4-B가 ①②를 흡수. ③(주간 SoV 재측정)은 리텐션 기능이라 전략 백로그의 "주간 재측정+이메일 알림"과 병합.

## 5. 오류 6유형 (운영 자동화)

| 코드 | 상황 | 처리 |
|------|------|------|
| CRON-401 | cron 인증 실패(secret/헤더 없음) | 401 (keep-alive와 동일 패턴 재사용) |
| CRON-409 | 스윕 중복 실행(동시 두 인스턴스) | updateMany count 기반 멱등 처리, 이중정리 무해 |
| CRON-422 | stuck 판정 임계 오설정(정상 job 오탐) | 임계를 넉넉히(15분+), 로그로 오탐 모니터 |
| CRON-500 | 스윕 중 DB 오류 | 부분 실패 허용, 다음 주기 재시도(cron 특성상 자동) |
| CRON-503 | Vercel cron 미발화(스케줄 누락) | vercel.json crons 등록 확인 + keep-alive로 발화 자체는 검증됨 |
| ADMIN-403 | 콘솔에 비-admin 접근 | Clerk admin 역할 체크, 비admin 차단 |
