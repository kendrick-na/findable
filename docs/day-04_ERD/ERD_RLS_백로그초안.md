## 1. ERD — 실제 스키마 기준 (9 모델)

### 1.1 엔티티 관계도 (텍스트 ERD)

```
                    ┌─────────────────┐
                    │  Organization   │  (Clerk org = 워크스페이스)
                    │  id (uuid) PK   │
                    │  ownerId(Clerk) │
                    │  plan/billing…  │
                    └───┬────┬────┬───┘
              1:N       │    │    │       1:N
        ┌───────────────┘    │    └───────────────┐
        ▼                    ▼ 1:N                 ▼
   ┌─────────┐         ┌──────────┐          ┌──────────┐
   │  User   │         │  Brand   │          │  Report  │  (org 또는 brand에 귀속)
   │ id(Clerk)│        │ id PK    │◄────┐    │ type/pdf │
   │ email U │         │ orgId FK │     │    └──────────┘
   └─────────┘         │ domain   │     │ 1:N (brandId nullable)
                       │ competitors│    │
                       │ =JSON!   │     │
                       │ entityVariants JSON
                       └──┬────┬──┘     │
                    1:N   │    │  1:N   │
              ┌───────────┘    └──────┐ │
              ▼                       ▼ │
        ┌──────────┐            ┌──────────┐
        │  Prompt  │            │ Tracking │◄──── Engine (N:1, 시드 7개)
        │ brandId  │───1:N─────▶│ brandId  │      id: chatgpt/claude/
        │ text/lang│  (promptId)│ promptId │      perplexity/gemini/
        │ category │            │ engineId │      hyperclova/naver/daum
        └──────────┘            │ brandMentioned
                                │ mentionPosition
                                │ sentiment
                                │ citedSources JSON
                                │ shareOfVoice(SoV)
                                │ errorMessage
                                └──────────┘

  ┌── 비로그인/PLG 진입점 (org 없음) ────────────────┐
  │  AuditJob                     Lead              │
  │  email/domain                 email/source      │
  │  status(queued→…)             (CRM 진입)         │
  │  result JSON (휴리스틱)                          │
  │  crewStatus/crewResult(4에이전트)                │
  │  ipAddress (rate limit)                          │
  └──────────────────────────────────────────────────┘
```

### 1.2 Day03 추상 엔티티 → 실제 모델 매핑 [확인사실]

| Day03 전달표(추상) | 실제 스키마 모델 | 차이 / 비고 |
|---|---|---|
| `user` | **User** | id=Clerk user_id, email @unique. organizationId nullable |
| `organization` | **Organization** | Clerk org. plan·billing 필드 다수(Toss/PayPal) |
| `audit` | **AuditJob** | ⚠️이름 다름. + crew 4에이전트 모드·ipAddress rate limit·email |
| `measurement` | **Tracking** | ⚠️이름 다름. 훨씬 리치(sentiment·mentionPosition·citedSources·errorMessage) |
| `brand` | **Brand** | + industry·language·entityVariants(한국어 엔티티 그라운딩) |
| `competitor` | ❌**테이블 아님** | Brand.competitors = **JSON 필드** `[{name, domain}]` |
| (전달표 누락) | **Prompt** | 브랜드별 추적 프롬프트. category 7종·isAutoGenerated |
| (전달표 누락) | **Engine** | 시드 7개(chatgpt·claude·perplexity·gemini·hyperclova·naver·daum) |
| (전달표 누락) | **Report** | free_audit·weekly·monthly·custom. pdfUrl·data JSON |
| (전달표 누락) | **Lead** | CRM 진입. source(free_audit·contact·newsletter·referral) |

### 1.3 핵심 관계 [확인사실]
- `Organization 1:N User` — org 없는 User 허용(가입 직후, organizationId nullable)
- `Organization 1:N Brand 1:N Prompt` — 브랜드가 추적 대상, 프롬프트가 질의 단위
- `Tracking = Brand × Prompt × Engine` 교차 — SoV 측정의 원자 레코드(모든 엔진 호출 raw+분석)
- `Report`는 brandId·organizationId **둘 다 nullable** — free_audit(brand 전)도 담을 수 있게
- `AuditJob·Lead`는 org 밖 — **비로그인 PLG 진입점**(권한경계 §2에서 별도 취급)

### 1.4 관측된 설계 결정 [확인사실→검토]
- **`competitor`가 정규 테이블이 아니라 JSON** → 경쟁사 SoV를 브랜드처럼 시계열 추적하려면 정규화 필요할 수 있음. **Should("경쟁사 벤치마크")가 v1 승격되면 스키마 변경 대상** → 백로그 등록(§5).
- **`relationMode = "prisma"`** → Neon에서 FK 제약을 DB가 아닌 Prisma가 관리. RLS를 DB레벨로 못 건다는 뜻 = §2의 **앱레벨 스코핑이 유일한 격리 수단**임을 스키마가 이미 확정.
- **`entityVariants`(한국어 엔티티 그라운딩)** — "아모레/Amorepacific/아모레퍼시픽" 동의어. Findable 한국어 차별화가 **스키마에 이미 반영**돼 있음(Day02 USP 검증).

## 2. 권한 경계 (RLS 치환 = Clerk org + Prisma 앱레벨 스코핑)

> ⚠️ 커리큘럼은 Supabase Row Level Security(DB가 정책으로 행 필터) 전제.
> Findable은 Neon+Prisma+`relationMode="prisma"` → **DB레벨 RLS 없음**. 대신 **모든 쿼리에 `organizationId` 스코핑을 앱 코드가 강제**한다. 이게 유일한 격리선이라 누락=조직 간 데이터 노출(PRD §5 보안 리스크 "상").

### 2.1 역할 [확인사실 = Clerk]
| 역할 | 출처 | 권한 |
|---|---|---|
| **org owner** | Clerk org(`ownerId`) | 자기 org 전체 CRUD + billing |
| **org member** | Clerk org role | 자기 org의 brand·prompt·tracking·report 조회/생성 |
| **익명(비로그인)** | org 없음 | AuditJob 생성만(무료 진단 1회), 결과는 email로만 |

### 2.2 엔티티별 접근 규칙 (앱레벨 강제)

| 모델 | 격리 키 | 규칙 |
|---|---|---|
| Organization | id = Clerk org | 본인 소속 org만 |
| User | organizationId | 같은 org 멤버만 조회 |
| Brand | organizationId | **모든 read/write에 `where: { organizationId }` 필수** |
| Prompt | brand.organizationId | brandId로 접근 시 상위 org 확인 |
| Tracking | brand.organizationId | 직접 orgId 없음 → **brand 경유 스코핑**(조인 시 누락 주의) ⚠️ |
| Report | organizationId ∥ brandId | 둘 중 하나로 org 확인 |
| Engine | (전역 시드) | 읽기 전용, 격리 불필요 |
| **AuditJob** | ❌org 없음 | 익명. **email·ipAddress로만 식별** + rate limit |
| **Lead** | ❌org 없음 | CRM 내부용. 앱 사용자 노출 안 함 |

### 2.3 ⚠️ 위험 지점 (앱레벨의 함정) [가정→Day11 검증]
1. **`Tracking`에 직접 `organizationId`가 없음** → brand 조인 없이 `trackingId`로 바로 조회하면 격리 우회 가능. → **모든 Tracking 쿼리는 brand.organizationId 확인을 거쳐야** 함. Day11 구현 시 헬퍼(`scopedTracking(orgId)`)로 강제.
2. **JSON 필드(`competitors`·`citedSources`)는 권한 필터 불가** → 민감정보 넣지 말 것.
3. **AuditJob 남용** — 비로그인이라 org 방어선 없음 → `ipAddress` rate limit이 유일 방어. [확인필요] 현재 실제로 rate limit 걸려있나 = Day11/Day18 점검.
4. **Prisma `relationMode="prisma"`** = onDelete Cascade도 앱이 처리 → 삭제 시 고아 레코드 위험. Day18 런북 대상.

> 🔍 **[Day04 재검토 제안 — 미확정]**: 앱레벨 스코핑은 실수 한 번=유출. 장기적으로 **Prisma 미들웨어/Extension으로 org 스코핑 자동 주입**(모든 쿼리에 where 강제)을 Day11에 검토. 현재는 제안만(원 구조 유지).
