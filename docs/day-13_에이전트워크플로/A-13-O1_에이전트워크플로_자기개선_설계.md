## 1. 현재 워크플로 구조 [확인사실]

```
                 ┌─────────────────────────────────────┐
   AuditJob      │  runCrewDiagnose(input: CrewInput)   │
  (빠른모드      │                                     │
   result)  ───► │   Promise.allSettled([               │
                 │     runMinji  (한국 엔진)   ┐        │
                 │     runAlex   (영어 엔진)   │ 병렬    │
                 │     runSujin  (인용 출처)   ┘        │
                 │   ])                                 │
                 │        │                             │
                 │        ▼                             │
                 │   runJunho(analysts) ── 종합 →       │
                 │        StrategistOutput              │
                 └─────────────────────────────────────┘
                          │
                          ▼
                 AuditJob.crewResult (Json) 저장
```

- **형태: 단방향 파이프라인(feed-forward).** analysts → strategist 로 한 번 흐르고 끝.
- 각 에이전트는 `Agent.generate([...], { structuredOutput: { schema } })`로 Zod 스키마 강제(AI SDK v6 structured output).
- 모델: `anthropic/claude-sonnet-4.6`(기본) · `anthropic/claude-haiku-4.5`(fast, **현재 미사용** — `void MODEL_FAST`).
- 부분 실패 허용: `allSettled` → 1명 실패해도 stub 폴백, jobId 결과 유지.

## 2. "자기개선 루프"를 새로 설계 (블라인드 — 현재 구현 안 보고 먼저 그림)

교과서적 self-improving agent workflow는 최소 이 4요소를 갖는다:

| 요소 | 정의 | 왜 필요한가 |
|------|------|------------|
| **① 생성(Generate)** | 에이전트가 초안 산출물 생성 | 현재도 있음 |
| **② 자기평가(Critique/Reflect)** | 산출물을 룰/스키마/사실성 기준으로 스스로 채점 | 틀린 답을 그대로 내보내지 않기 위해 |
| **③ 개선(Refine)** | 평가 피드백을 받아 재생성 | 1회 생성보다 품질↑ (reflection 패턴) |
| **④ 종료 조건(Stop)** | 점수 임계 도달 or 최대 N회 → 루프 종료 | 무한루프·비용폭주 방지 |

이 4요소를 Findable crew에 매핑하면:

```
runAgent(생성) → selfCritique(평가) → 통과? ─예→ 다음 단계
                        │
                        └─아니오→ refine(피드백 주입 재생성) ──┐
                        ▲                                      │
                        └──────────── N회 미만이면 반복 ◄──────┘
```

추가로 **crew 레벨의 루프**도 가능:
- 준호(전략가)가 "analysts 근거가 부족하다"고 판단하면 → **특정 analyst를 재호출**(방향 재조준).
- 이게 진짜 "에이전트형 워크플로"의 자기개선 — 지금은 없음.

## 3. 현재 구현과 대조 = 발견 (★핵심)

### D13-1 [확인사실] **자기개선 루프가 아예 없음 — 순수 feed-forward**
- 준호 출력이 다시 analysts로 돌아가는 경로 **없음**. analysts끼리도 서로 참조 안 함.
- ②자기평가·③개선·④종료조건 **전부 부재**. 각 에이전트는 1회 생성이 끝.
- → "에이전트형 워크플로"라기보다 **병렬 함수 3개 + 종합 함수 1개**. 자율성(스스로 판단해 재시도/재조준)이 없음.
- **함의**: LLM이 스키마는 맞췄지만 내용이 부실/환각이어도 그대로 `crewResult`에 저장 → 사용자에게 노출.

### D13-2 [확인사실] **주석과 코드 불일치 — "재시도 1회 + 타임아웃 60초"는 코드에 없음** (반쪽 구현)
- `orchestrator.ts:16` 주석: `재시도 1회 + 타임아웃 60초 가드 (안정성)`.
- 실제 검증: `grep -rn "setTimeout|AbortController|retry|maxRetries|Promise.race" packages/ai/lib/crew/` → **0건**.
- → 주석이 약속한 안정성 가드가 **구현되지 않음**. Day12 D12-3("정의만 있고 사용처 0")과 같은 계열의 "반쪽 잇기".
- **함의**: 에이전트 호출이 60초 넘게 매달려도 끊을 장치 없음. `Agent.generate`가 무응답이면 무한 대기 가능.

### D13-3 [확인사실] **크래시 복구 불가 — `after()` 백그라운드 + status 영구 stuck**
- `crew-runner.ts`: `crewStatus="processing"` 세팅 → crew 실행 → 성공 시 `completed`/실패 시 `failed`.
- 그러나 **프로세스가 중간에 죽으면**(배포 롤링·타임아웃·크래시) `catch`가 안 걸려 `crewStatus`가 **`processing`에 영구히 멈춤**. 재개(resume)·재시도 스케줄 없음.
- 300초 함수 타임아웃(Vercel 기본) 초과 가능성: crew는 주석상 "2~10분" 소요 → **10분이면 타임아웃 확정**.
- **함의**: 자기개선은커녕 **crash-safe 실행조차 안 됨**. 이건 durable workflow 문제([[reference_vercel_workflow]] 영역).

### D13-4 [AI가설] **fast 모델 미사용 = 자기평가 단계의 준비된 재료가 놀고 있음**
- `MODEL_FAST`(haiku-4.5) 정의됐지만 `void MODEL_FAST`로 명시적 미사용.
- 자기개선 루프의 ②자기평가는 **싸고 빠른 모델(haiku)로 채점**하는 게 정석(생성=sonnet, 평가=haiku). 재료는 이미 있음.
- → 루프 도입 시 별도 모델 발급 불필요. **[확인필요]**: haiku-4.5로 critique 품질이 충분한지 실측.

## 4. 설계 제안 — Findable crew에 자기개선 루프 얹기 (미확정, §7.3)

### 4-A. 에이전트 레벨: analyst 자기평가 1패스 (저~중위험)
```
runAnalyst(생성, sonnet)
   → selfCritique(haiku): "findings가 데이터를 실제 인용하는가?
      whyItMatters 50자 규칙 지키나? dataGaps 정직한가?" → score 0~100 + 사유
   → score < 임계(예 70)면 refine 1회(피드백 주입 재생성)
   → 최대 1회만 (④종료조건: N=1, 비용 가드)
```
- 왜 crew 전체 루프가 아니라 analyst 개별 1패스부터? → **비용·지연 폭발 방지.** 지금도 "2~10분"인데 crew 전체 반복은 실서비스 비현실적.

### 4-B. crew 레벨: 준호의 "근거 부족" 재조준 (고위험 — 보류)
- 준호가 특정 analyst 근거 부족 판정 시 해당 analyst 1회 재호출.
- ⚠️ 지연·비용 예측 어려움 → **실고객 검증 후**에만.

### 4-C. 안정성 가드 먼저 (D13-2/D13-3 해소 — P0)
- 자기개선보다 **먼저** 고쳐야 할 것: 타임아웃 가드 + 크래시 복구.
- 주석이 약속만 하고 없는 재시도·타임아웃을 **실제 구현**하거나, 주석을 걷어냄(거짓 약속 제거).
- durable 실행은 Vercel Workflow(WDK) 후보 — Day16 배포 트랙과 연계 검토.

### 종료 조건(④) 설계 규칙 — 무한루프 방지
- 최대 반복 N = 1 (analyst 자기개선), crew 레벨은 0(보류).
- 각 refine 호출 전 **비용/시간 예산 체크** → 초과 시 현재 산출물로 조기 종료 + `dataGaps`에 "품질 미검증" 명시(정직 표기).
