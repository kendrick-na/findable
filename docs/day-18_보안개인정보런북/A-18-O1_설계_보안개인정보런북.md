## 1. 블라인드 재검증 — 실측 발견 (★ 4건)

### D18-1 [확인사실] ★PIPA — IP주소를 수집·저장하나 처리방침에 **완전 미고지**
- **실제 수집**: `apps/web/app/api/audit/route.ts:146` — `x-forwarded-for`/`x-real-ip`로 IP 추출 → `auditJob.create({ data: { ipAddress } })`. schema.prisma:172 `ipAddress String? // 어뷰즈 방지`.
- **고지 상태**: `apps/web/app/[locale]/legal/[slug]/page.tsx` 개인정보 처리방침 §1 수집항목 = **"이메일·도메인·(유료)카드결제정보·사용로그"뿐. IP주소 문자열 0건**(grep 확인).
- **결함**: 실제 수집 ⊋ 고지 수집. IP는 개인정보(PIPA상 위치정보·식별 가능) → **수집·이용 고지 의무 위반 소지**. 어뷰즈 방지 목적은 정당하나 **고지·보존기간 명시가 없음**.
- 영향: 개인정보 분쟁·신고 시 리스크. 지원사업·B2B 계약(파트너 승인) 실사에서 감점 요인.

### D18-2 [확인사실] ★PIPA — 결제 위탁사 방침 ≠ 실제
- **실제 결제**: `@portone/browser-sdk/v2`(`apps/web/app/[locale]/checkout/page.tsx:12`) + `api.portone.io`(`packages/payments/portone.ts:23`). = **PortOne V2**.
- **고지 상태**: 처리방침 §1 "카드 결제 정보(**토스페이먼츠** 위탁)", 이용약관 제4조 "**토스페이먼츠 또는 PayPal**".
- **결함**: 개인정보 처리위탁 고지는 **수탁사 실명 정확성**이 핵심인데 실제(PortOne)와 불일치.
- ✅ **[확인사실] 실제 활성 PG = PortOne 단독**(2026-07-29 재검증): PortOne=`apps/web` checkout+verify 실경로 / Stripe=`apps/api` webhook에만(next-forge 잔재)·**api 미배포라 실동작 안 함**. → 방침엔 PortOne만 표기하면 됨. (PortOne↔카드사 위탁 체인 상세만 경미한 [확인필요], "포트원 통해 처리"로 포괄 가능.) 방침엔 셋 다 정확히 없음.

### D18-3 [확인사실] 보안 인프라는 양호 — 편중 없음
- **Arcjet**(`packages/security`): `shield(mode:LIVE)` + `detectBot(mode:LIVE)` — web·app proxy에 실연결(`apps/web/proxy.ts:34`). 공통 공격·봇 차단 라이브.
- **Rate limit**: 두 층. ①Arcjet IP 기반(인프라) ②`checkUsageGate`(route.ts 내) = **DB 기반 24시간 도메인 1회 무료진단 게이트**(429 반환) + 파트너 하루1회. 어뷰즈 방지 도메인 정합.
- **Secret**: `apps/web/.env.local` = `git check-ignore` 통과(추적 안 됨). CLAUDE.md §3 secret 규칙 준수. [[feedback_api_key_no_chat_output]] 원칙과 일치.
- **Upstash rate-limit 패키지**: 정의돼 있으나 audit route는 자체 usageGate 사용 → **Upstash는 env.ts 참조만, 실사용처 미미**(D17 계열 반쪽구현이나 여기선 자체 게이트가 대체하므로 결함 아님, 중복 후보).

### D18-4 [확인사실] 런북(장애 대응 절차) 문서 부재
- `docs/`에 런북·incident·장애대응 문서 0건(grep). Day16 A-16-O1에서 "롤백 런북=Day18 연계"로 넘긴 항목.
- **현재 대응 흐름은 암묵지**: 장애 → (알림 없음, D17-5) → 사후 로그 발견 → 대표 1인이 즉흥 대응. **재현 가능한 절차 없음** = 1인 의존·야간 취약.
- 있는 재료: Vercel Instant Rollback(D16), Sentry(예외 캡처), stuck-sweep cron(D17), 개인정보 책임자(방침 §6=대표). → 재료는 있으나 **한 장의 절차로 안 묶임**.

## 3. 판단 — 오늘 가장 가치 있는 개입

**보안(A-)은 이미 견고. 진짜 gap은 개인정보 정합(C)과 런북(D).**

1. **D18-1·2 개인정보 처리방침 정합(P0·저위험·문서수정)** — IP 수집 고지 추가 + 결제 위탁사 실명 정정. **실코드가 아니라 legal 페이지 텍스트**라 저위험. 라이브 서비스의 법적 리스크를 즉시 낮춤. 다만 법조항 인용은 계약/사실 프레이밍으로([[feedback_law_notation]] 준수, "제OO조" 표기).
2. **D18-4 최소 런북(P1·문서)** — 장애 유형별 1페이지 대응 절차. Day17 운영자 알림(BL-Day17-02)과 세트로 "알림→대응" 완성.

→ 개인정보 정합은 **오늘 반영 가능한 최우선 후보**(코드 아닌 legal 텍스트, 사용자 확인 후). 런북은 문서 신규작성이라 병행 가능.

**⚠️ §7.3 준수**: legal 페이지도 라이브(www.findable.co.kr/ko/legal/privacy)이므로 **문안 확정 = 사용자 확인 후**. 특히 결제 위탁 체인(PortOne↔카드사)·IP 보존기간은 [확인필요] 해소 후 확정. 이번 산출물은 재검증·정정안 초안까지.
