## 오늘 한 일
Findable 실코드를 보안/개인정보/런북 3축으로 블라인드 재검증. 보안 인프라(Arcjet·usageGate·secret 위생)는 이미 견고 → 오늘의 진짜 발견은 **개인정보 처리방침이 실제 코드와 어긋난 것**과 **런북 부재**.

## ★ 핵심 발견 4건 (→ A-18-O1)
- **D18-1 (★PIPA)** IP주소를 실제 수집·저장(route.ts:146, schema:172)하나 처리방침 §1 수집항목에 **완전 미고지**(grep 0건). = 수집 고지 의무 위반 소지.
- **D18-2 (★PIPA)** 결제 위탁사 방침(토스페이먼츠/PayPal) ≠ 실제(PortOne V2). payments 패키지엔 Stripe도 초기화 → 실제 활성 PG [확인필요].
- **D18-3** 보안 인프라 양호: Arcjet shield+봇탐지 LIVE·usageGate(DB 24h 1회 429)·secret gitignore 정합. 편중 없음(A-).
- **D18-4** 런북 부재: 장애 대응이 대표 1인 암묵지. 재료(Vercel Rollback·Sentry·stuck cron)는 있으나 절차로 안 묶임.

## 핵심 교훈 3가지
1. **처리방침은 마케팅 문구가 아니라 코드의 거울이다.** "실제 수집 = 고지 수집"이 PIPA의 핵심인데, 코드가 조용히 IP를 더 수집하면 방침이 자동으로 거짓말이 된다. Day17 교훈("명세만 판정은 시점의존")의 개인정보판 — 방침도 코드로 재검증해야 한다.
2. **방침에 보존기간을 쓰면 파기 로직도 있어야 정합.** 안 그러면 방침이 또 거짓말(D18-1 후속). 문서와 코드는 한 몸.
3. **알림(D17-5)과 런북(D18-4)은 세트다.** 알림만 있고 절차 없으면 새벽 3시에 알림 보고도 뭘 할지 모른다. 절차만 있고 알림 없으면 장애를 늦게 안다. 둘 다 있어야 대응이 완성.

## [확인사실] — 2026-07-29 코드 재검증 완료 (기존 [확인필요] 해소)
- ✅ **실제 활성 PG = PortOne 단독**. Stripe는 apps/api webhook 잔재(next-forge)이나 api 미배포라 실동작 안 함. → 방침엔 PortOne만.
