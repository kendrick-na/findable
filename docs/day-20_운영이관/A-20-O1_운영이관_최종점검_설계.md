# A-20-O1 — 운영 이관 + 최종 점검 (설계·재검증)

> Day20 (2026-07-30). 4주차 마지막 = 프로덕션 운영 이관·최종 점검.
> 강의 원문 없어 커리큘럼 맵 + 실제 git/배포/cron 상태 실측 기준.
> ⚠️ 실습 규칙 §7.3 준수: apps/·packages/·schema **미변경**. 커밋·머지·배포는 outward-facing → 사용자 명시 승인 없이 실행 금지.

---

## 1. 오늘의 대상 — "운영 이관"이란 무엇인가

커리큘럼상 Day20 = **운영 이관 + 최종 점검**. Day16(배포·CI)·17(로그·알림)·18(보안·런북)·19(릴리스노트)가 각각 하나씩 세운 "프로덕션 운영의 조각"을, 오늘 **하나의 이관 가능한 상태로 묶고 최종 점검**하는 날.

"운영 이관"의 두 의미:
1. **개발 → 프로덕션 이관**: feature 브랜치에 쌓인 것을 main(프로덕션)으로 안전하게 넘김.
2. **팀·운영자 이관**: 1인 대표가 암묵지로 들고 있던 운영을, 문서(런북·릴리스노트·인덱스)로 재현 가능하게 넘김. (지금은 대표 1인이라 "미래의 나 or 첫 합류자에게 넘길 수 있는가"가 기준)

어제 스페셜세션3(한기용) 강의의 Team Building·온보딩 첫 90일과 정확히 같은 문제 — **운영을 사람에 묶지 않고 문서·절차에 묶어야 이관이 된다.**

---

## 2. ★ 블라인드 재검증 — 실측 발견 4건

기존 문서(Day16~19 A-*-O2 명세, 릴리스노트, 런북)의 **주장**을 오늘 실제 git/cron/배포 상태로 대조.

### D20-1 — 프로덕션 격차가 오히려 벌어짐 (릴리스노트 [확인필요] 정정)
- Day19 A-19-O1 = "feature가 main보다 **13커밋 앞**". 릴리스노트 초안도 "13커밋" 명시.
- **실측(2026-07-30)**: `git rev-list --count main..HEAD` = **33커밋**. 20커밋 더 벌어짐.
- 그동안 세션E-2·E-3가 대량 작업(로그인 안정화·결제→plan 자동화·출시차단 5건·측정결함 24건 대청소·엔진 7개 완전체 등)을 feature에 계속 쌓음.
- → **릴리스노트의 "13커밋"은 이미 낡음.** 최종 점검 = 릴리스노트를 **33커밋 기준으로 갱신**하는 것이 첫 번째 이관 작업.

### D20-2 — 미커밋이 111 → 5로 정리됨 (Day19 D19-3 해소 확인)
- Day19 = "미커밋 111파일(modified 61·untracked 50)" = 유실·뒤섞임 위험 최고.
- **실측**: 미커밋 = **5개, 전부 modified, untracked 0**.
  - `apps/app/(authenticated)/lib/dashboard-data.ts`, `page.tsx`
  - `apps/app/lib/db/scoped.ts` (org 스코핑 헬퍼 — Day11·12 최대 위험 지점)
  - `apps/web/audit/[jobId]/components/copilot-chat.tsx`
  - `packages/ai/lib/engines/naver-briefing-adapter.ts`
- untracked 0 = Day17에서 지적한 "관측 사각지대(sweep·digest cron이 git 밖)"가 **커밋되어 해소됨**.
- → Day19의 최대 리스크(111파일 뒤섞임)는 **다른 세션이 이미 커밋으로 정리**. 남은 5개는 성격 확인 후 다음 커밋 경계에 포함 여부 판단.

### D20-3 — Day17 sweep 이중구현이 정리됨 (cron 실측)
- Day17 D17-1 = "sweep-stuck-jobs가 web·api 이중구현 + 둘 다 untracked".
- **실측 cron 3개(전부 커밋됨)**:
  - `apps/web/app/api/cron/sweep-stuck-jobs/route.ts` — 스케줄 `0 1 * * *` (web/vercel.json)
  - `apps/web/app/api/cron/daily-ops-digest/route.ts` — 스케줄 `0 0 * * *` (Day14 집계 cron 계열)
  - `apps/api/app/cron/keep-alive/route.ts` — 스케줄 `0 1 * * *` (api/vercel.json, Neon 보온)
- → sweep은 **web 정본으로 수렴**(Day17 P0 "안A web 정본 권장"대로), api쪽 중복 sweep은 보이지 않음. Day13~16 내내 "명세만"이던 stuck 스윕 cron이 **실코드로 존재·커밋·스케줄 등록 완료**. Day14 P0 최종 반영 확인.
- ⚠️ [확인필요] www.findable.co.kr = web 배포 → web cron은 실행됨. **api 배포 여부 불명** → keep-alive 실제 실행 여부는 미확인(Day17부터 미해결 [확인필요] 유지).

### D20-4 — 운영 4각(배포·알림·런북·릴리스)은 문서로 섰으나, "이관 리허설"은 0회
- Day16 배포 / Day17 알림 / Day18 런북 / Day19 릴리스노트 = 각 산출물 존재.
- **그러나 실제 이관 시나리오를 한 번도 리허설 안 함**: main 머지 → 배포 → 릴리스노트 확정 → 롤백 판단, 이 사이클을 문서만 있고 돌려본 적 없음.
- 런북 §1(사이트다운=Vercel Rollback)도 "가능하다"만 있고 실행 로그 0.
- → 이관의 마지막 = **문서를 신뢰할 수 있는지 한 번 돌려보는 것**. 지금 단계에선 실배포 리허설은 고위험이라, "체크리스트 기반 드라이런(문서 위에서 순서 검증)"으로 대체.

## 3. 핵심 교훈

1. **이관 = 격차를 0으로 만드는 게 아니라, 격차를 아는 상태로 만드는 것.** 33커밋이 문제가 아니라, "33커밋에 무엇이 들었는지 릴리스노트가 아는가"가 이관 준비도. (Day19 "릴리스노트=롤백의 지도"의 연장)
2. **"명세만" 판정은 시점 의존** — Day13~16 내내 "sweep cron 미반영"이라 적었는데 D20-3에서 커밋·스케줄까지 완료 확인. Day17 교훈(매 Day 실코드 재검증) 재확인.
3. **운영 이관과 팀 이관은 같은 문제** — 어제 강의(온보딩 90일·Team Building)와 오늘 실습(런북·인덱스로 운영 넘기기)이 겹침. 사람에 묶인 운영은 이관 불가.

## 4. Findable 운영 이관 준비도 — 최종 점검 스코어카드

| 운영 영역 | 산출물 | 상태 | 이관 가능? |
|---|---|---|---|
| 배포 (Day16) | Vercel Git 자동배포 (web·app·api 3프로젝트 분리) | LIVE | △ main 머지 절차 미문서 |
| 로그·알림 (Day17) | Logtail·Sentry·PostHog·Knock 연결 | 부분 (알림 트리거 0, D17-5 운영자 알림 부재) | △ |
| 보안·개인정보 (Day18) | 처리방침 정정(IP·PortOne)·런북 5유형 | 문서 완료, 미배포 | ○ 문서 |
| 릴리스 (Day19) | 릴리스노트 (형식 확립) | 초안 존재, **13커밋 기준 낡음(D20-1)** | △ 갱신 필요 |
| stuck 스윕 (Day13~16 P0) | sweep-stuck-jobs cron | **커밋·스케줄 완료(D20-3)** | ○ |
| 프로덕션 격차 | main..feature | **33커밋 미반영(D20-1)** | ✗ 미이관 |

**결론**: 문서(런북·릴리스노트·인덱스)는 이관 가능한 형태. **막힌 지점은 코드 이관 = 33커밋을 main으로 넘기는 릴리스 결정**(고위험, 사용자 승인 필수). 최종 점검의 산출물 = 릴리스노트 33커밋 갱신 + 이관 체크리스트 드라이런.
