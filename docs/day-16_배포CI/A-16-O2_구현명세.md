# A-16-O2 — Day16 구현 명세 (stuck 스윕 cron · CI 게이트)

> 명세 확정, 실코드 미반영(라이브 §7.3). keep-alive 인증 패턴·AuditJob 스키마 실측 기반.

## 1. stuck 스윕 cron (⬜ 실코드 반영 최우선 후보)

### 1-1. 목적
`after()` 백그라운드 crew가 함수 300초 상한(D16-4)에 끊겨 crewStatus="processing"으로 굳는 job을, 사용자 재조회 없이도 주기적으로 정리한다. 기존 route/runner의 stale 가드(Day13/15, 사용자 조회 시점 의존)의 2차 안전망.

### 1-2. 위치·파일 (신규)
- `apps/api/app/cron/sweep-stuck-jobs/route.ts` (신규, keep-alive 형제)
- `apps/api/vercel.json` crons에 항목 1개 추가

### 1-3. 인증 (keep-alive 패턴 그대로 재사용)
```ts
const cronSecret = process.env.CRON_SECRET;
const authHeader = request.headers.get("authorization");
const isVercelCron = request.headers.get("x-vercel-cron") === "1";
const authorized = cronSecret ? authHeader === `Bearer ${cronSecret}` : isVercelCron;
if (!authorized) return new Response("Unauthorized", { status: 401 });
```

### 1-4. 스윕 로직 (명세)
AuditJob 실측 필드 사용: `status`(AuditStatus: queued/processing/completed/failed), `crewStatus`(CrewStatus: not_requested/... /processing/...), `createdAt`, `crewStartedAt`. 인덱스 `@@index([status])`·`@@index([createdAt])` 존재 → 쿼리 저비용.

```ts
const STALE_MS = 15 * 60 * 1000; // 15분. route stale 가드와 동일 임계
const now = Date.now();
const cutoff = new Date(now - STALE_MS);

// ① 빠른 진단(status) stuck: queued/processing인데 createdAt 15분 초과
const r1 = await database.auditJob.updateMany({
  where: {
    status: { in: ["queued", "processing"] },
    createdAt: { lt: cutoff },
  },
  data: { status: "failed", errorMessage: "stuck timeout swept by cron" },
});

// ② crew stuck: crewStatus="processing"인데 crewStartedAt 15분 초과
const r2 = await database.auditJob.updateMany({
  where: {
    crewStatus: "processing",
    crewStartedAt: { lt: cutoff },
  },
  data: { crewStatus: "failed" }, // errorMessage는 빠른모드 전용 → crew는 crewStatus만
});

return Response.json({ swept: { status: r1.count, crew: r2.count } });
```

**멱등성·안전성 근거**
- `updateMany` = 조건 맞는 행만 갱신. 이미 failed/completed면 where에서 빠짐 → 중복 실행해도 무해(멱등).
- 스키마 무변경(기존 필드·인덱스만 사용).
- ⚠️ **crewStartedAt=null인 queued 굳음 사각지대**는 이미 Day15 커밋 2ce7f1b가 "queued 전환 시 crewStartedAt 세팅"으로 메움 → ②가 그 job도 잡음. cron은 그 위의 3차 방어.
- ⚠️ 15분 임계: 정상 crew는 함수 300초(5분) 내 끝나야 정상이므로 15분이면 확실히 죽은 것. [확인필요] 실측 crew 평균 소요시간으로 임계 재조정.

### 1-5. vercel.json 추가 (명세)
```jsonc
"crons": [
  { "path": "/cron/keep-alive", "schedule": "0 1 * * *" },
  { "path": "/cron/sweep-stuck-jobs", "schedule": "*/15 * * * *" } // 15분마다
]
```
⚠️ **[확인필요] Vercel 플랜 제약**: Hobby는 cron이 하루 1회로 제한될 수 있음. 15분 주기(`*/15`)는 Pro 필요 가능성.
- **주기 대안(Hobby일 경우)**: keep-alive(매일 01:00) 안에 스윕 로직을 합쳐 "하루 1회 정리"로 격하 → stuck job이 최대 24시간 남지만, 사용자 재조회 stale 가드(Day13/15)가 1차 방어라 치명적이진 않음. cron은 어디까지나 백업.

## 2. GitHub Actions 최소 CI 게이트 (🟡 제안, 미도입)

### 2-1. 위치 (신규, 현재 부재)
`.github/workflows/ci.yml`

### 2-2. 명세
```yaml
name: CI
on:
  pull_request:
  push:
    branches: [main]
jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2   # Findable = bunVersion 1.x
      - run: bun install --frozen-lockfile
      - run: bunx turbo lint typecheck  # build는 Vercel이 담당 → 중복 배제
```
- **빌드 제외 이유**: Vercel이 이미 push마다 `next build` 수행. Actions에서 또 빌드하면 시간·크레딧 이중 소모. lint/typecheck만 앞당겨 PR에서 잡는다.
- **미도입 이유**: 현재 1인·feature 브랜치 직접 배포. 게이트 이득 < 유지비용. 기여자 2인+ 또는 main 보호 규칙 도입 시 활성화. **지금은 파일 안 만듦(설계만).**
