# 리포트 발행 화면 「회사 카드 매출 불러오기」 버튼 설계안 (구현 전 · 대표 승인 대기)

작성: 측정 준비도 게이트 개발 세션, 2026-10-16. 코드는 아직 한 줄도 만들지 않았다.

## 1. 한 줄 결론

발행 화면(`/admin/client-reports`)에 버튼 하나를 둔다. 누르면 이 측정 회차의 회사를 **사업자번호로 먼저, 없으면 도메인으로** 회사 카드에서 찾아 매출을 가져오고, 리포트의 `copy.revenue_opportunity` 초안을 만들어 판별 JSON 칸에 **미리보기로 보여 준다**. 사람이 확인하고 "넣기"를 눌러야 JSON에 들어간다. 후보가 둘 이상이거나 값이 안 맞으면 자동으로 정하지 않고 사람이 고른다.

## 2. 지금 상태 (코드로 확인한 사실)

| 항목 | 현재 |
|---|---|
| 리포트의 매출 칸 | `review.copy.revenue_opportunity`. **사람이 직접 적는다**(넘버즈인 초안에 DART 접수번호가 수기로 들어 있음). `admin.ts`에는 매출 참조가 없다. |
| 공식 | 연매출 × 7% × (1 − 정확 노출률). `packages/audit/revenue-opportunity.ts`의 `aiRoutedRevenue`가 단일 출처이고 호출처는 아직 없다. |
| 회사 카드의 매출 | 오늘 만든 기능: 카드에서 `공시에서 찾기`·`직접 입력` → `CompanyFact(field=revenue)` 저장. 값에 사업연도·출처·접수번호·연결/별도가 붙는다. |
| 변환기 | `company-revenue.ts`: 카드 매출 → `aiRoutedRevenue`. 넘버즈인 시험에서 수기 값과 일치(놓치는 연 매출만 1원 반올림 차). |
| 발행 화면 | `issue-form.tsx`: 회차 ID(auditJobId) + 판별 JSON 붙여넣기 → 미리보기/발행. |

## 3. 버튼 위치와 동작

위치: 발행 화면의 「판별 JSON」 입력칸 바로 위. 회차 ID를 넣으면 활성화.

흐름:

1. **[회사 카드 매출 불러오기]** 클릭 → 서버가 회차(`AuditJob`)에서 `domain`, `brandId`를 읽는다.
2. **회사 찾기** (4절의 키 규칙). 결과는 셋 중 하나.
   - 한 곳이 확정 → 3번으로.
   - 후보 여러 곳 → 후보 목록(회사명·사업자번호·도메인)을 보여 주고 사람이 고른다. 자동 선택 안 함.
   - 없음 → "회사 카드에 없음. 영업 회사 카드에서 먼저 매출을 찾거나 입력하세요" + 카드 링크.
3. **매출 확인**: 그 회사의 `CompanyFact(revenue)` 중 사업연도 최신, **연결 우선·없으면 별도**를 고른다. 없으면 "카드에 매출 없음"(숫자를 만들지 않음).
4. **미리보기 패널**(저장 전): 회사명, 연결 근거(예: `사업자번호 833-87-01017 일치`), 매출(약 3,249.6억 · 2025 연결 · 공시 기준 · 접수번호), 계산 결과(AI 경유 연 227.5억 등).
   - 놓치는 비율(1 − 정확 노출률)은 **사람이 판별한 JSON(review)이 있을 때만** 계산한다. 판별이 없으면 연 매출·AI 경유 매출까지만 보여 준다.
5. **[JSON에 넣기]** 클릭 → 판별 JSON의 `copy.revenue_opportunity`만 채운다. 다른 칸은 건드리지 않는다. 기존에 사람이 적은 값이 있으면 **덮어쓰기 전에 비교해 보여 주고 확인**을 받는다(대표 규칙: 확정 값 임의 변경 금지).
6. 발행은 기존 흐름 그대로. 시스템이 매출을 자동으로 발행시키지 않는다.

## 4. 회차 ↔ 회사 카드를 잇는 키: 후보 비교

| | A. 사업자번호 | B. 도메인 |
|---|---|---|
| 어디서 | `Brand.businessNumber`(고객 입력) 또는 측정 때 푸터에서 읽어 저장한 `officialSiteIdentity.businessNumber` ↔ `Company.businessNumber`(유니크) | `AuditJob.domain`/`Brand.domain` ↔ `Company.domain` |
| 장점 | 법인을 정확히 특정(유니크 키). 체크섬 검증 가능. 영업 카드 매출이 사업자번호 기준으로 이미 모인다. | 추가 입력 없이 항상 있다. 영업 카드의 측정 연결이 이미 도메인(`www.` 포함) 기준. |
| 단점 | 푸터가 비면 번호가 없다(프란츠 번호 빔, 프롬맘 상호 빔). 한 사이트에 번호가 둘(입점몰·운영사 병기)일 수 있다. | 같은 도메인에 다른 법인(운영사≠브랜드사), 도메인 변경·여러 개, `Company.domain`이 비어 있는 회사가 있다. |
| 오연결 위험 | 낮음(번호가 하나로 확정될 때) | 중간(법인이 다른 경우) |

**추천: A 우선 → 없으면 B(후보로만) → 사람 확인.**

- 번호가 하나로 확정되고 체크섬을 통과하며 카드에 같은 번호의 회사가 있으면 → "확정 후보"로 미리보기까지 진행(그래도 넣기는 사람이 누른다).
- 번호가 없거나 둘 이상이면 → 도메인으로 찾은 회사들을 **후보 목록**으로만 보여 준다.
- 화면에 항상 **연결 근거**(어떤 키로 이었는지)를 적고, 넣을 때 `basis` 문구에 남긴다. 나중에 "왜 이 회사 매출이냐"에 답하기 위함.

## 5. 대표 판단이 필요한 점

1. 버튼을 **발행 화면에 추가**해도 되는지(화면 변경).
2. 기존에 사람이 적은 `revenue_opportunity`가 있을 때: **덮어쓰기 전에 비교 확인**(추천) vs 아예 덮어쓰지 않기.
3. 놓치는 비율을 시스템 자동판정이 아니라 **사람이 검수한 판별 기준**으로만 계산(추천). 같은 브랜드에서 자동 4/56과 사람 9/56이 달랐던 실측이 있다.

## 7. 이미 관제탑 방침과 맞물린 점

- 대표 원칙 「리포트의 모든 데이터는 시스템에서 뽑을 수 있어야 한다」의 매출 부분이 이 버튼으로 닫힌다.
- 푸터에서 상호·번호를 읽는 일은 새로 만들지 않고 이미 측정 때마다 저장되는 `officialSiteIdentity`를 쓴다(체크섬·국세청 확인 단계는 이 버튼 범위 밖, 후속).
