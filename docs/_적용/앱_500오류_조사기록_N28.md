> 결론: **코드 문제가 아니다. `app.findable.co.kr` 도메인으로 접속할 때만 난다.**
> 👤 Clerk 대시보드 설정 확인이 필요하다(§4).

## 1. 증상 (실측)

로그인한 상태로 대시보드에 들어가면 **"Oops, something went wrong"** 화면이 뜬다.

```
동시 요청 부하(4페이지 × 5라운드 = 20회):
  app.findable.co.kr  → 🔴 500 이 4/20 (20%)
  같은 빌드의 배포 URL → ✅ 500 이 0/20
```

Vercel 로그:
```
Clerk: Unable to verify request, this usually means the Clerk middleware did not run.
(code=auth_signature_invalid)
```

⚠️ **단발 요청으로는 거의 안 잡힌다.** 동시 요청을 던져야 재현된다.
   → 실사용자 1명이 탭을 여러 개 열거나, 페이지를 빠르게 이동할 때 걸린다.

## 3. ⚠️ 이 결론에 이르기까지 **오진 4번** (같은 실수 반복 금지)

| # | 가설 | 왜 틀렸나 |
|:--:|---|---|
| 1 | Vercel Analytics 404 → Clerk 미들웨어 우회 | Clerk 공식 문서가 이 사슬을 설명해서 그럴듯했다. **404 를 0건으로 만들었는데 500 이 그대로 3/12** |
| 2 | 내 ④ 병렬화(`auth()` 를 `Promise.all` 로)가 원인 | 1단을 되돌려도 남았고, **손도 안 댄 `/billing`·`/brand` 가 깨졌다** |
| 3 | matcher 에 `/__clerk/(.*)` 추가한 것이 원인 | 빼도 500 이 남았다 |
| 4 | DB 헬퍼가 내부에서 `auth()` 를 불러 동시 호출된다 | 병렬화를 **전면 철회**했는데도 3/24 로 남았다 |

⭐ **갈라준 것은 "같은 빌드 · 도메인 vs 배포 URL" 대조 하나였다.**
🎓 교훈: *"내 변경 이후 나타났다"* 는 **원인의 증거가 아니다.** 변수를 하나만 남기고 대조해야 한다.
   (배포본을 비교할 때 **도메인 차이를 같이 바꿔버려서** 3번을 헛짚었다)

## 4. 👤 확인이 필요한 것 (Clerk 대시보드)

코드로 더 파는 것은 근거 없는 추측이 된다. 아래는 **설정 영역**이다:

1. **Clerk 프로덕션 인스턴스의 도메인 설정** — `app.findable.co.kr` 이 정식 등록돼 있나
2. **DNS CNAME(`clerk.`·`accounts.` 등) 전파 상태** — Clerk 프로덕션은 CNAME 레코드를 요구한다
3. **`CLERK_PROXY_URL` / `CLERK_DOMAIN` 이 설정돼 있나** — 둘을 **동시에 설정하면 안 된다**(문서 명시)
4. **satellite 도메인 설정 여부** — `www.findable.co.kr`(web)과 `app.findable.co.kr`(app)이
   같은 Clerk 인스턴스를 쓴다면 satellite 구성이 필요할 수 있다

📕 근거 문서(2026-08-13 확인):
- clerk.com/docs/guides/development/deployment/production
- clerk.com/docs/guides/dashboard/dns-domains/satellite-domains
- clerk.com/docs/guides/dashboard/dns-domains/proxy-fapi

## 5. ✅ 이번에 실제로 고친 것 (독립적으로 옳은 것만 남겼다)

- **Vercel Analytics 404 제거** — 프로젝트에서 Web Analytics 가 비활성인데 코드가 스크립트를
  요청해 `/_vercel/insights/script.js` 가 **web·app 양쪽 404**였다. 지표는 하나도 안 쌓이고
  있었으므로 잃는 것이 없다. `NEXT_PUBLIC_ENABLE_VERCEL_ANALYTICS=1` 로 다시 켤 수 있게 했다.
  ⚠️ 켜기 전 **Vercel 프로젝트에서 Web Analytics 활성화 먼저**.

## 6. ⛔ 되돌린 것 (되살리지 말 것)

- **④ 홈·`/actions` 병렬화** — 500 의 원인은 아니었지만, `scoped.ts` 헬퍼가 내부에서
  `auth()` 를 부르므로 "DB 쿼리만 병렬화"도 실제로는 인증 동시 호출이다. **효과가 검증되지
  않은 채 위험만 남는 변경**이라 철회했다.
- **matcher `/__clerk/(.*)`** — 문서 권장이지만 우리 앱에서 효과 0(우리는 `frontendApiProxy`
  를 안 쓴다). 프로덕션 인증 경로를 근거 없이 유지하지 않는다.

## 7. 📌 남은 과제
