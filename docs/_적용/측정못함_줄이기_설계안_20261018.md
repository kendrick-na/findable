# '측정 못 함' 줄이기 + 질문 생성 플래그 켜는 순서 — 설계안 (구현 전 · 대표 승인 대기)

작성: 측정 준비도 게이트 개발 세션, 2026-10-18. 관제탑 전달 대표 원칙: **"애초에 측정하지 못할 오류를 만들면 안 된다."** 코드 변경 없음. 화면(UI)을 건드리는 제안은 따로 표시했고 구현 전에 시안 승인을 받는다.

## 0. 한 줄 결론

**세 겹으로 막는다: ① 측정을 시작하기 전에 못 잴 조건을 걸러 내고, ② 호출 단계에서 429·시간 초과가 안 나게 속도를 조절하고, ③ 그래도 실패한 칸은 같은 실행 안에서 다시 묻는다.** 지금은 ③이 '시간 초과'에만 있고(그것도 별도 회차가 있을 때만), 429·미연결·빈 응답은 재시도 없이 '측정 못 함'으로 남는다. **새 화면은 필요 없다**(이미 있는 "반영 예정" 표시를 재사용). 질문 생성 플래그 3개(③⑥⑨)는 **③ → ⑥ → ⑨ 순서**로, 켜기 전에 52곳 재측정 대상 16곳으로 A/B 비교를 먼저 한다.

> 철칙(저장소의 최다 사고 유형): **못 잰 것을 0이나 '미노출'로 세지 않는다.** 아래 모든 제안은 "재시도 후에도 못 재면 분모에서 뺀다 + 이유를 기록"을 지킨다. 예외는 '검색 결과가 정말 0건'(다음·네이버)처럼 **사실로 확인된 것**뿐이다.

## 2. 줄이는 설계

### 2-1. ① 시작 전 점검(preflight) — "못 잴 걸 만들지 않는다" (규모 S~M)
- 측정 시작 직전에 **엔진별로 지금 호출 가능한가**를 점검한다: 키·연결 설정 존재(C), Letsur 유닛 잔량·차단기 상태(이미 `tripLetsurCircuit` 있음), 같은 시각 다른 회차가 한도를 쓰고 있는지.
- 못 부르는 엔진은 계획에서 **미리 빼고 결과에 "이번 회차 제외 엔진: X(사유)"로 기록**한다(측정 중에 오류로 쏟아지지 않게). 질문 수·사이트 읽기 결과(①⑧)도 이 점검 결과에 같이 남긴다.
- 화면: **새 UI 없음**(기존 "측정 못 한 엔진" 표시가 쓰는 데이터에 사유만 늘어남).

### 2-2. ② 엔진별 호출 속도 조절 — 429를 안 만든다 (규모 M)
- 지금: 한 회차는 질문마다 엔진당 **동시 1개**만 보내 429를 피한다. 하지만 **여러 회차(고객·영업·무료 진단)가 동시에 돌면 같은 공급자에 겹쳐** 한도를 넘는다(회차 사이 조율 없음).
- 제안: 엔진별 **분당 호출 상한을 회차들이 공유**한다. 저장소에 이미 `packages/rate-limit`(Upstash 슬라이딩 윈도우)이 있어 **새 패키지 없이** 쓸 수 있다(운영에서 실제 켜져 있는지는 방침 세션도 미확인이라 **확인 필요**). 상한은 공급자별 한도의 약 70%로 시작(실제 한도는 대시보드 확인 필요).
- 한도에 닿으면 **대기 후 호출**(최대 N초, 예산 270초 안에서). 429를 받으면 응답의 `Retry-After`를 따른다(`describeProviderError`가 이미 추출). 위험: 대기가 총 시간을 늘림 → 예산 계산에 반영해야 함.
- 화면: 없음.

### 2-3. ③ 실패 칸을 같은 실행 안에서 다시 묻기 (규모 M)
| 대상 | 방법 | 한도 |
|---|---|---|
| A2·B(429·5xx·네트워크) | 칸이 실패하면 **다시 묻기 대기열**로 보내고, 해당 질문 배치가 끝난 뒤 칸당 **최대 2회** 재시도. 간격은 **2초 → 8초**(지터), 429면 `Retry-After` 우선 | 칸당 2회, 엔진당 동시 2(기존 `LATE_CELL_REASK_PER_ENGINE_CONCURRENCY`) |
| C(미연결) | 재시도하지 않음(2-1에서 미리 걸러짐) | 0 |
| D(빈 응답) | **빈 문자열을 오류("empty answer")로 바꾸고** 위와 같은 재시도 대상에 넣는다(ChatGPT 경로와 동일하게) | 칸당 2회 |
| E(검색 API 실패) | 즉시 1회 재시도(1초 뒤). 검색 API는 빠르고 원가가 거의 없음 | 1회 |
- 이미 있는 "다시 묻기 회차"(별도 함수 호출 300초, 칸당 1회 상한 200초)는 **그대로 유지**하고, 그 회차가 **없는 실행**(A2: 로컬 측정·관리자 1건)에서만 이 인라인 재시도를 쓴다(예산 남을 때). → 같은 칸을 두 번 유료 호출하는 일이 없도록 **칸 상태에 시도 횟수를 기록**한다.
- 칸 상태 표현: 새 상태를 만들지 않고 기존 `timed_out_pending`("반영 예정")에 **재시도 대기**를 같은 의미로 재사용 → **화면 변화 0**(고객은 이미 "반영 예정"을 본다). 최종 실패는 기존처럼 분모에서 빠지고 엔진 이름으로 표시.
- 비용: 재시도는 유료 호출이다. 0.3%(타임아웃)+α 수준이면 회차당 수 건이라 원가 영향은 작다(시산: 회차 100칸 × 1% × 2회 ≈ 2회 호출 ≈ 수십 원 수준, **실측으로 확인 필요**). 원가 상한을 칸당 2회로 못 박는다.

### 2-4. 측정 못 한 칸의 표기 원칙
재시도 후에도 못 잰 칸은 **분모에서 빼고 사유(타임아웃·429·빈 응답·연결 안 됨)를 ⑦ 기록에 남긴다.** '모른다·미노출'로 세지 않는다(이 원칙을 테스트로 고정: 오류 칸이 `absent`로 바뀌는 경로 0).

### 2-5. 단계·규모·승인

| 단계 | 내용 | 규모 | 비고 |
|---|---|---|---|
| 1 | 빈 응답을 오류로(D) + 테스트 | S (0.5일) | 측정 결과에 영향(빈 답이 '미노출'에서 '측정 못 함·재시도'로) → **재측정 때만 반영**, 대표 승인 |
| 2 | 검색 API 즉시 재시도(E) | S (0.5일) | |
| 3 | 인라인 재시도(A2·B) + 칸 시도 기록 | M (2일) | 다시 묻기 회차와 중복 방지가 핵심 |
| 4 | preflight(2-1) | S~M (1.5일) | |
| 5 | 엔진별 속도 조절(2-2) | M (2일) | Upstash 사용 가능 여부 확인 후 |
| 합계 | | 약 6~7일 | 단계마다 대표 승인, **UI 변화 없음** |

## 3. 질문 생성 플래그(③⑥⑨) 켜는 순서·검증 계획

### 3-1. 켜는 순서와 이유
| 순서 | 플래그 | 영향 범위 | 이유 |
|---|---|---|---|
| 1 | `QUESTION_OTHER_FALLBACK_ENABLED` (③) | 업종이 '기타'·미지정인 곳만. 업종 10개 경로는 바이트 불변(테스트로 고정) | **영향 범위가 가장 작고** 지금 0문항인 곳을 채운다 |
| 2 | `QUESTION_BRAND_GUARANTEE_ENABLED` (⑥) | 이름 질문이 0개일 때만 | 이름 질문이 있는 곳은 불변 |
| 3 | `QUESTION_SOFT_CONFIDENCE_ENABLED` (⑨) | 생성기가 "확신 없음"을 낸 모든 곳(통과 질문 8개 이상일 때) | **영향 범위가 가장 넓다** — 가장 마지막. 비확신이 흔한 업종에서 결과 변화가 큼 |

플래그는 `findable-app`(질문 제안 서버 액션)의 환경변수다. 켜기 순서는 **Preview(Neon 복사본) → 운영** 이고, 되돌리기는 **환경변수를 지우고 재배포(빈 커밋)** 한 줄이다. 플래그는 질문 후보만 바꾸고(사람이 고른 것만 저장), 이미 저장된 질문·측정 결과·DB는 건드리지 않아 **데이터 되돌릴 일이 없다.**

### 3-2. 켜기 전 검증 — 52곳 재측정 대상 16곳 A/B (외부 비용 호출 → 승인 필요)
- 대상: 52곳 세션의 미측정 6곳 + 질문 부족 12곳 중 재측정 후보 16곳(ID만 사용).
- 방법: **사이트 읽기 결과를 고정**(한 번 읽어 저장해 사이트 변동을 제거)한 뒤, 같은 입력으로 플래그 꺼짐/켜짐을 **각 3회**씩 생성(생성은 비결정적이라 1회로 판단하지 않는다 — 52곳 재현에서 같은 입력이 4→18개로 흔들림).
- 비교 지표(합격 기준 제안):
  | 지표 | 켜기 전(꺼짐) | 켜짐 합격선 |
  |---|---|---|
  | 질문 0개 | 현재값 | **0곳** |
  | 질문 8개 미만 | 현재값 | 감소, 증가 0 |
  | 이름 질문 0개 | 현재값 | **0곳** |
  | 기본 폴백(4개)으로 물러남 | 현재값 | 감소(⑨), 증가 0 |
  | 질문 품질(이름 없는 질문에 이름 섞임·지어낸 고유명사) | 현재 폐기율 | **악화 없음**(사람이 샘플 점검) |
  | 업종 10개 경로 | — | 출력 동일(자동 테스트) |
- 비용: 52곳 세션이 재현 진단에 **약 21회 호출 ≈ ₩600**을 썼다고 했으므로, 16곳 × 2조건 × 3회 = 96회 ≈ **₩2,800 내외(추정, 실제 단가로 재확인)**. 외부 비용 호출이라 **대표 승인 후**에만 실행한다. 실행 도구는 읽기 고정 + 생성 호출만 하는 별도 스크립트(저장소 코드 변경 없이 복사본)로 만든다.
- 합격 시: 플래그를 위 순서로 하나씩, **하루 간격으로** 켜고 각 단계에서 `prompt.suggest.guard_dropped` 로그와 폴백 비율을 확인한다.
- 재측정 표기: 질문 생성기가 바뀌므로 52곳 결과는 **'2차 측정(개선본)'으로 분리 표기**(기존 진단 문서의 주의 그대로). 비교 키(`questionSetKey` 등)가 달라져 이전 회차와 '비교 불가'가 되는 것은 의도된 동작이다.

## 4. 대표가 정할 일 (쉬운 말)
1. **재시도 한도**: 칸당 2회(2초·8초 간격)로 시작해도 될까요? (원가: 회차당 수십 원 수준 추정)
2. **'빈 응답'은 미노출이 아니라 '측정 못 함 → 다시 묻기'로 바꿀까요?** (제안: 예. 못 잰 것을 0으로 세지 않기 위해. 재측정 때부터 반영)
3. **엔진별 호출 속도 조절**을 넣을까요? (여러 회차가 겹칠 때 429를 막음. 대신 가끔 몇 초 기다립니다)
4. **플래그 켜기 전 16곳 A/B**(약 3천 원 내외 외부 호출)를 승인해 주세요.
5. 플래그 켜는 순서(③ → ⑥ → ⑨, 하루 간격) 확인.

## 5. 확인하지 못한 것
- Claude·Perplexity·Gemini(Gateway 어댑터)의 빈 응답이 실제로 몇 번 나는지: 코드 읽기로는 오류로 안 바뀌지만 발생 빈도는 ⑦ 기록 이후에 집계해야 한다.
