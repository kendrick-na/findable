# W1 효과 영수증 MVP 계약

상태: 계약 초안만 기록. W0-3 run identity/Tracking 계약과 실제 고객 재측정 전에는 영속 구현·UI 효과 판정을 하지 않는다.

## 목적

한 처방에 대해 고객이 확인할 수 있는 측정 전후 관찰을 남긴다. `before/after` 변화는 관찰값이며 처방의 인과 효과나 매출 효과가 아니다.

## 최소 계약

```ts
type EffectReceipt = {
  id: string;
  organizationId: string;
  brandId: string;
  actionCompletionId: string;
  actionKind: string;
  actionTarget: string;
  startedAt: string;
  completedAt: string;
  baselineRun: {
    auditJobId: string;
    runAt: string;
    questionPlanHash: string;
    engineIds: string[];
    verdictVersion: number;
    metric: string;
    value: number | null;
  };
  followupRun: {
    auditJobId: string;
    runAt: string;
    questionPlanHash: string;
    engineIds: string[];
    verdictVersion: number;
    metric: string;
    value: number | null;
  };
  comparability: {
    sameQuestionPlan: boolean;
    sameEngineSet: boolean;
    sameVerdictVersion: boolean;
    sameBrandScope: boolean;
  };
  observedChange: {
    metric: string;
    before: number | null;
    after: number | null;
    delta: number | null;
  };
  caveats: ["observed_change_not_causal", "no_control_group"];
};
```

## 생성 조건

- `ActionCompletion`이 현재 조직의 `brandId`·`kind`·`target`과 일치해야 한다.
- 기준 회차와 후속 회차가 모두 고객이 확인 가능한 `AuditJob`이어야 한다.
- 두 회차에 `auditJobId`, 실행 시각, 질문 계획 해시, 엔진 집합, 판정 버전이 있어야 한다.
- 비교 가능성 네 값이 모두 `true`가 아니면 영수증을 발행하지 않는다. 누락은 0이 아니라 `미확인`이다.
- 후속 측정의 시간 간격 정책은 제품 규칙으로 별도 확정하며, 간격만으로 인과를 주장하지 않는다.

## 현재 저장 경로의 제한

- `ActionCompletion`은 완료 시점과 점수 스냅샷만 가진다.
- `AuditJob`과 `Tracking`은 현재 공통 `completedAt/trackedAt` 값으로만 간접 연결된다. `auditJobId` FK와 run별 unique 멱등 키가 없다.
- `AuditJob.result`에는 `promptIndex`, `promptText`, `engineId`, `mentionVerdictVersion`이 있으나 질문 계획 해시·엔진 버전·실행 원장 계약으로 고정되어 있지 않다.
- W0-3 run identity와 `persistAuditTracking` 멱등성 계약이 확정되기 전에는 위 계약을 DB 스키마나 운영 write로 구현하지 않는다.

## 2026-10-04 추가 발견: 질문 순환과 비교 가능성의 충돌

현재 본 측정은 전체 8질문 한도 안에서 discovery 최대 2개를 먼저 배정하고, 남은 자리에 고객 저장 질문 중 가장 오래 측정하지 않은 질문을 순환해 넣는다(`RUNNER_PROMPT_LIMIT`, `resolveRunPrompts`, `pickRotatingPrompts`). 저장 질문이 한 회차 자리보다 많으면 다음 회차의 질문 집합이 달라질 수 있다. 따라서 위 `sameQuestionPlan` 조건을 두 **전체 회차의 합계 점수**에 그대로 적용하면, 실제로 영수증을 발행할 수 있는 쌍이 거의 없거나 없을 수 있다. 이것은 미검증 효과가 아니라 설계상 비교 불가능성이다.

제품 결정 후보는 다음과 같다. 현재 순환을 유지하면서 겹친 질문만 추려 비교하는 방법은 표본 선택 편향과 분모 변화를 설명하기 어려워 기본값으로 채택하지 않는다. 권장 설계 가설은 고객이 중요하다고 확인한 소수의 고정 질문 패널을 매 회차 같은 엔진·판정·검색 표본 버전으로 측정하고, 나머지 질문은 별도 순환 탐색 슬롯으로 유지하는 것이다. 고정 패널의 질문 수·추가 호출 비용·429/300초 예산·고객이 실제로 반복 확인할 지표는 W0-3 안정화와 고객 문제 검증 후 결정한다. 고정 패널이 없거나 실행 조건이 다르면 전체 점수 차이를 처방 효과 영수증으로 발행하지 않는다.

최소 수용 반례: 저장 질문 10개, 한 회차 브랜드 질문 자리 6개인 경우 연속 측정의 질문 집합이 달라질 수 있음을 고정한다. 같은 총점이라도 질문 또는 네이버 표본 버전이 다르면 `sameQuestionPlan=false` 또는 별도 comparability failure로 차단해야 한다. 한 질문만 겹쳤다는 이유로 전체 회차의 `delta`를 발행해서는 안 된다. 이 절은 계약·테스트 요구이며 제품 구현·실고객 효과 검증 완료를 뜻하지 않는다.

## UI 문구 규칙

표시 순서는 `관찰된 변화`와 `처방 인과 근거 없음`을 분리한다. 항상 다음 고지를 함께 표시한다.

> 이 변화는 같은 조건에서 관찰된 전후 차이입니다. 경쟁사 변동·측정 방식·외부 요인을 통제하지 않았고 대조군이 없어 처방의 인과 효과로 단정할 수 없습니다.

Report.data, PDF, Blob, 기존 저장 액션 원문은 이 계약을 위해 수정하지 않는다.
