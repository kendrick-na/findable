# W1 효과 영수증 MVP 계약

상태: 계약 초안만 기록. W0-3 run identity/Tracking 계약과 실제 고객 재측정 전에는 영속 구현·UI 효과 판정을 하지 않는다.

## 목적

한 처방에 대해 고객이 확인할 수 있는 측정 전후 관찰을 남긴다. `before/after` 변화는 관찰값이며 처방의 인과 효과나 매출 효과가 아니다.

## 최소 계약

```ts
type EffectReceipt = {
  id: string;
  organizationId: string;
  brandId: string;
  actionCompletionId: string;
  actionKind: string;
  actionTarget: string;
  startedAt: string;
  completedAt: string;
  baselineRun: {
    auditJobId: string;
    runAt: string;
    questionPlanHash: string;
    engineIds: string[];
    verdictVersion: number;
    metric: string;
    value: number | null;
  };
  followupRun: {
    auditJobId: string;
    runAt: string;
    questionPlanHash: string;
    engineIds: string[];
    verdictVersion: number;
    metric: string;
    value: number | null;
  };
  comparability: {
    sameQuestionPlan: boolean;
    sameEngineSet: boolean;
    sameVerdictVersion: boolean;
    sameBrandScope: boolean;
  };
  observedChange: {
    metric: string;
    before: number | null;
    after: number | null;
    delta: number | null;
  };
  caveats: ["observed_change_not_causal", "no_control_group"];
};
```

## 생성 조건

- `ActionCompletion`이 현재 조직의 `brandId`·`kind`·`target`과 일치해야 한다.
- 기준 회차와 후속 회차가 모두 고객이 확인 가능한 `AuditJob`이어야 한다.
- 두 회차에 `auditJobId`, 실행 시각, 질문 계획 해시, 엔진 집합, 판정 버전이 있어야 한다.
- 비교 가능성 네 값이 모두 `true`가 아니면 영수증을 발행하지 않는다. 누락은 0이 아니라 `미확인`이다.
- 후속 측정의 시간 간격 정책은 제품 규칙으로 별도 확정하며, 간격만으로 인과를 주장하지 않는다.

## 현재 저장 경로의 제한

- `ActionCompletion`은 완료 시점과 점수 스냅샷만 가진다.
- `AuditJob`과 `Tracking`은 현재 공통 `completedAt/trackedAt` 값으로만 간접 연결된다. `auditJobId` FK와 run별 unique 멱등 키가 없다.
- `AuditJob.result`에는 `promptIndex`, `promptText`, `engineId`, `mentionVerdictVersion`이 있으나 질문 계획 해시·엔진 버전·실행 원장 계약으로 고정되어 있지 않다.
- W0-3 run identity와 `persistAuditTracking` 멱등성 계약이 확정되기 전에는 위 계약을 DB 스키마나 운영 write로 구현하지 않는다.

## 2026-10-04 추가 발견: 질문 순환과 비교 가능성의 충돌

현재 본 측정은 전체 8질문 한도 안에서 discovery 최대 2개를 먼저 배정하고, 남은 자리에 고객 저장 질문 중 가장 오래 측정하지 않은 질문을 순환해 넣는다(`RUNNER_PROMPT_LIMIT`, `resolveRunPrompts`, `pickRotatingPrompts`). 저장 질문이 한 회차 자리보다 많으면 다음 회차의 질문 집합이 달라질 수 있다. 따라서 위 `sameQuestionPlan` 조건을 두 **전체 회차의 합계 점수**에 그대로 적용하면, 실제로 영수증을 발행할 수 있는 쌍이 거의 없거나 없을 수 있다. 이것은 미검증 효과가 아니라 설계상 비교 불가능성이다.

제품 결정 후보는 다음과 같다. 현재 순환을 유지하면서 겹친 질문만 추려 비교하는 방법은 표본 선택 편향과 분모 변화를 설명하기 어려워 기본값으로 채택하지 않는다. 권장 설계 가설은 고객이 중요하다고 확인한 소수의 고정 질문 패널을 매 회차 같은 엔진·판정·검색 표본 버전으로 측정하고, 나머지 질문은 별도 순환 탐색 슬롯으로 유지하는 것이다. 고정 패널의 질문 수·추가 호출 비용·429/300초 예산·고객이 실제로 반복 확인할 지표는 W0-3 안정화와 고객 문제 검증 후 결정한다. 고정 패널이 없거나 실행 조건이 다르면 전체 점수 차이를 처방 효과 영수증으로 발행하지 않는다.

최소 수용 반례: 저장 질문 10개, 한 회차 브랜드 질문 자리 6개인 경우 연속 측정의 질문 집합이 달라질 수 있음을 고정한다. 같은 총점이라도 질문 또는 네이버 표본 버전이 다르면 `sameQuestionPlan=false` 또는 별도 comparability failure로 차단해야 한다. 한 질문만 겹쳤다는 이유로 전체 회차의 `delta`를 발행해서는 안 된다. 이 절은 계약·테스트 요구이며 제품 구현·실고객 효과 검증 완료를 뜻하지 않는다.

## 독립 제품 반박 후 범위 결정 (2026-10-04, Claude Code READ-ONLY)

고정 질문 패널도 본 측정의 8칸 안에 넣으면 순환 탐색 자리가 줄고, 패널의 브랜드 수준 점수 변화가 특정 액션 때문인 것처럼 읽힐 수 있다. discovery 수가 회차마다 0~2개로 달라져 저장 질문 자리도 변한다. `lastTrackedAt`은 성공 Tracking 행을 통해 계산하므로 실패 질문은 다시 선택될 수 있다. 동일 시각의 DB 반환 순서 의존은 `5649230`에서 영속 질문 ID 동률 정렬로 제거했지만, discovery·실패·라운드로빈에 따른 두 회차 질문 계획 차이까지 해결한 것은 아니다. 이는 위 계약의 질문 계획 동일성을 자동으로 보장하지 못하는 추가 이유다.

`5649230` 후속 반례(로컬 의도 RED 확인): 저장 질문 9개가 모두 `lastTrackedAt=null`, 실행 자리 8개라면 ID가 작은 8개를 선택한다. 그 8개의 모든 응답이 실패·stub·판정보류여서 Tracking이 남지 않으면 다음 실행도 같은 8개를 선택하며 9번째는 계속 측정되지 않는다. `prompt-rotation.test.ts`에 이 조건을 일시 추가해 **1 RED/기존 4 PASS**를 재현한 뒤 후보 checkout의 통과 기준을 오염시키지 않도록 그 임시 테스트 변경은 제거했다. 이 문제는 기존 동률 비결정성을 되돌려 해결할 수 없으며, 질문별 **시도 사실**을 성공 Tracking과 구별해 지속 기록하고 반복 실패의 재시도/쿨다운/상한 및 crash·동시 실행 시 원자성을 정의해야 한다. 현재 `Prompt`에는 마지막 시도 시각 칸이 없고 W0-0 운영 migration 대상도 미확정이므로 이 설계·스키마를 임의 운영 적용하지 않는다. 고객에게 약속한 저장 질문 순환 커버리지와 후속 측정 신뢰성의 출시 게이트로 남긴다.

### 질문 시도 원장 최소 불변식 (W0-3 연계 설계, 미구현)

현재 W0-3 checkpoint는 한 Job 안에서 선택된 `prompts`·엔진 계획·완료된 질문 배치를 보존하고 lease token으로 늦은 writer를 차단한다. 반면 다음 Job의 질문 선택은 성공 `Tracking.trackedAt`만 읽는다. 그러므로 checkpoint를 성공 Tracking으로 간주하거나 실패 응답을 Tracking에 억지로 저장하면 안 된다. 두 목적을 분리한 `PromptAttempt` 계열 원장이 필요하다.

- 키: `(auditJobId, promptId)` 유일. `brandId`, 단조 `selectionSeq`, 계획 순번, `selectedAt`, `startedAt`, `finishedAt`, 결과(`completed | failed | unverified`), 당시 lease/run identity를 보존한다. 이 행은 호출 전에는 **선택 의도**일 뿐 실제 제공자 시도를 뜻하지 않으며, `startedAt` 이후에만 Findable이 호출을 시작한 **dispatch attempt**라고 부른다. discovery 질문은 저장 Prompt가 아니므로 이 원장의 고객 저장 질문 순환 분모에 넣지 않는다.
- 최초 계획 생성은 **같은 DB transaction**에서 live AuditJob lease를 확인하고, 브랜드 단위 선택 잠금을 잡아 질문을 고른 뒤 `reserved` 행과 동일 질문 계획 checkpoint를 함께 기록한다. transaction 전 crash는 둘 다 없고, transaction 후 crash는 둘 다 남아 resume이 같은 계획을 쓴다.
- 각 질문의 유료 호출 직전 live lease로 `startedAt`을 단조 기록한다. 외부 제공자 호출은 DB transaction 안에 넣지 않는다. 호출 완료 뒤 전체 질문 배치 checkpoint 저장과 `finishedAt/outcome` 갱신은 같은 fenced transaction으로 묶는다. zombie lease는 어느 기록도 갱신하지 못한다.
- 다음 Job의 순환 기준은 성공 Tracking이 아니라 최근 **내구 선택 순서**(`selectionSeq`)다. 같은 시각·동시 실행에서도 순서를 잃지 않아야 하며, 실패해도 다음 새 Job은 선택된 질문을 뒤로 보낸다. 다만 선택만 되고 시작되지 않은 행은 유효 checkpoint가 재개하거나 lease 만료 후 회수해야 하며 실제 제공자 시도·측정 완료로 세지 않는다. 제공자 수신 여부까지 exactly-once로 증명할 수 없으므로 `startedAt`은 “Findable이 호출을 내구적으로 시작함”만 뜻한다.
- 같은 브랜드의 동시 Job 두 개가 같은 질문을 예약하지 않도록 선택·예약 transaction을 직렬화한다. DB 잠금 동안 외부 호출은 금지한다. 반복 실패의 즉시 재호출 폭주를 막는 cooldown/최대 연속 실패 수는 제품·원가 정책이며 수치 근거 전 임의 확정하지 않는다.

현재 W0-3 v2 checkpoint의 질문 계획은 문장 중심이므로 이 원장과 결합하려면 저장 질문에 안정적 `promptId`를 포함하고 resume 때 일치 여부를 검증해야 한다. 전환 시 이미 실행 중일 수 있는 v2 Job을 약 24시간 호환해 재개할지, 안전하게 배수하고 새 버전만 받게 할지는 W0-0 운영 대상과 함께 정한다. 과거 성공 Tracking에서 선택 이력을 추정 소급하지 않는다.

필수 RED 매트릭스: (1) 9질문/8자리/8개 전부 실패 뒤 다음 Job에서 9번째 도달, (2) 선택 전 crash는 의도·checkpoint 모두 없음, (3) 선택 의도+checkpoint 뒤 crash는 같은 계획 resume, (4) 호출 시작 뒤 crash는 dispatch attempt 1회 보존, (5) 같은 브랜드 동시 Job의 선택 집합 비중복, (6) 늦은 lease의 started/finished 쓰기 0건, (7) checkpoint 저장 실패 시 finish rollback, (8) 실패·판정보류 원장이 AI 노출 성공 Tracking/점수에 포함되지 않음. W0-0의 실제 migration 대상과 W0-3의 300초·lease 후보가 확정되기 전에는 구현·배포 완료로 세지 않는다.

`prompt-attempt-ledger.ts`는 이 계약 중 DB와 무관한 상태 전이를 실행 가능한 순수 모델로 고정한다. 먼저 모듈 부재 RED를 확인한 뒤, 실패한 8개도 내구 `selectionSeq`로 뒤로 보내 9번째 질문에 도달하는 순환, 같은 Job 계획 재개, 선택/dispatch/성공의 분리, lease 불일치 writer 무효화, 시작 전 finish 거부, failed·unverified 성공 집계 제외를 단위 테스트로 GREEN 처리했다. 이는 스키마·transaction·브랜드 잠금·checkpoint 원자성·lease 인계·외부 호출 exactly-once를 구현한 것이 아니며 러너에는 연결하지 않았다. 특히 lease 만료 뒤 **선택됐지만 시작되지 않은** 계획을 새 lease가 인수할 때 기존 행의 fence를 어떤 원자 규칙으로 교체할지는 W0-3 lease 계약과 함께 RED로 먼저 확정해야 한다.

후속 순수 상태 반례는 부분 계획을 정상 resume으로 받아들이는 경우, 같은
`auditJobId`가 다른 브랜드에서 재사용되는 경우, 만료 lease의 미완료 행을 새
fence로 옮길 방법이 없는 경우를 **3 RED/기존 6 PASS**로 재현했다. 각 행에 같은
`planSize`를 보존해 누락·비연속 계획을 fail-closed하고, 브랜드 안의
`selectionSeq` 중복과 cross-brand Job 충돌을 거부하며, 명시적 takeover에서
미완료 행의 lease token만 CAS 대상이 되도록 한 순수 계약은 attempt+rotation
**13/13 GREEN**이다. Claude Code의 정확 SHA 후속 반박으로 행 token만 비교하면
lease 만료 후 takeover 전 좀비 쓰기를 막지 못하고, 후임 lease가 선임이 시작한
호출을 `completed`로 위조할 수 있음을 확인했다. 후속 순수 계약은 Job의 권위 있는
`leaseToken/leaseUntil`과 기록 시각을 함께 요구하고, 만료 old/live current 조합만
takeover하며, 삭제된 질문·축소된 limit·혼합 미완료 lease·불일치 selectedAt 재개를
fail-closed한다. 선임 lease가 시작한 미상 호출은 후임이 `completed/failed/unverified`로
종결하지 못하고 `abandoned`만 기록할 수 있다. stable ID 동률 비교도 locale 의존
`localeCompare` 대신 동일한 이진 비교로 고정했다. app **167 files / 1111 tests**와
audit/app typecheck·대상 Biome·diff check가 통과했다. `attemptNo`는 1을 보존하지만
`attemptNo+1` 재시도 행 생성·원자 CAS는 아직 영속 계층 RED가 필요하다. 실제 DB의
expired-lease 확인·원자 CAS·브랜드별 sequence 유일 제약·checkpoint 동시 갱신이
없으면 이 함수만으로 zombie 차단이나 동시 예약 안전성을 주장하지 않는다.

`PROMPT_ATTEMPT_LEDGER_ENABLED="true"`.** off(기본)면 러너는 두 테이블을 읽지도 쓰지도
않는다. 일회용 PG에서 RED 1~8과 정책·플래그 off 내성을 검증했으나 운영 DB에는 적용하지 않았다.

따라서 현재 `EffectReceipt` 타입은 **향후 비교 가능성의 상한 계약**이지 출시 가능한 전체 점수 영수증이 아니다. 기본 제품에서 브랜드 전체 `delta`를 특정 액션의 효과로 발행하는 기능은 보류한다. 더 좁은 대안 가설은 고객이 액션을 시작할 때 대상 질문·언어·엔진 1~3개를 명시적으로 잠그고, 본 측정의 순환 탐색과 분리해 전후의 질문×엔진 원문·판정·확인 가능한 인용을 나란히 보여 주는 것이다. 이것도 인과 효과, 매출 증가 또는 모델 자체의 고정성을 증명하지 않는다. 네이버 검색 표본/브리핑은 별도 정의가 검증되기 전에는 이 비교에 합산하지 않는다.

이 대안을 구현하기 전에는 W0-3 실행 identity·멱등성, 별도 측정의 제공자 호출 원가/429/300초 예산, 조치 기록과 후속 측정 시점, 실제 고객이 원문 비교를 의사결정·재방문에 쓰는지 확인해야 한다. 과거 원문을 현재 판정기로 재판정하는 방법은 버전 차이를 줄일 수 있지만 과거 발행본 수치와 충돌할 수 있으므로 원본·발행 당시 판정·재판정 버전을 모두 보존하고 W0-2 정책과 대조하기 전에는 적용하지 않는다. `2회 기준선`이나 `실패 칸 절반` 같은 표본/발행 임계값은 근거가 없어 아직 제품 규칙으로 채택하지 않는다.

## UI 문구 규칙

표시 순서는 `관찰된 변화`와 `처방 인과 근거 없음`을 분리한다. 항상 다음 고지를 함께 표시한다.

> 이 변화는 같은 조건에서 관찰된 전후 차이입니다. 경쟁사 변동·측정 방식·외부 요인을 통제하지 않았고 대조군이 없어 처방의 인과 효과로 단정할 수 없습니다.
