# 블로그 플랫폼 — 외부 벤치마크·Build vs Adopt 결정서 (2026-08-22)

## 결론

**기존 Prisma·Clerk·Postgres 축에서 직접 구축한다.** 목표는 단순 블로그가 아니라
Findable의 SEO/GEO 진단·액션가이드를 실제 공개 콘텐츠 발행까지 연결하는
**최적화 퍼블리싱 플랫폼**이다. 새 CMS를 넣으면 기존 측정 데이터와 별도로 ORM·마이그레이션·인증·
테넌트 권한을 다시 운영하게 된다. 대신 Substack·Medium의 퍼블리셔 네트워크 UX, Payload의
버전·권한 모델, Apostrophe의 contributor → editor → publish 흐름을 설계 기준으로 쓴다.

## 후보 판정

| 후보 | 판정 | 근거 |
|---|---|---|
| Payload CMS | Reference, 도입 보류 | Next.js native이고 draft/version/access control이 강점([GitHub](https://github.com/payloadcms/payload)). 그러나 Postgres 계층은 [Drizzle](https://payloadcms.com/docs/database/postgres)라 현재 Prisma와 이중화된다. |
| ApostropheCMS | Reference | contributor가 초안을 내고 editor가 검토·발행하며 preview와 version history를 제공한다([공식 workflow](https://apostrophecms.com/product/editorial-workflow)). |
| Sanity | Reference | draft/published·release·preview 개념은 좋지만 외부 저장소 추가가 측정 데이터의 단일 진실을 깬다. |
| Strapi·Directus | Reject for MVP | 범용 CMS/API·권한을 새로 운영하고 복잡한 승인 흐름은 커스텀 구현이 필요하다. |

| Keystatic·TinaCMS | Reject | Git 기반 편집에는 적합하지만 DB 권한·비공개 초안·발행 잡에는 부적합하다. |

## 공개 정책 경계

Google은 호스트 사이트 순위 신호를 이용하려는 목적으로 제3자 페이지를 싣는 것을 site reputation
abuse로 본다. 편집 관여 여부만으로 예외가 되지 않는다.
([공식 정책](https://developers.google.com/search/docs/essentials/spam-policies),
[정책 명확화](https://developers.google.com/search/blog/2024/11/site-reputation-abuse))

따라서 제품 포지셔닝은 "Findable 도메인 권위를 빌려주는 SEO 대행"이 아니라
**SEO/GEO 진단에서 나온 근거 기반 콘텐츠를 퍼블리셔 명의로 발행·측정·개선하는 네트워크**여야 한다.
고객사 글도 색인 가능한 공개 글이 될 수 있지만, 발행 전 품질·출처·중복·링크 남용 검사를 통과해야 한다.

- `publisher_draft`: Findable 또는 고객사 퍼블리셔의 비공개 초안.
- `publisher_review`: 퍼블리셔가 직접 검토·수정·승인하는 단계.
- `quality_check`: 중복·키워드 반복·출처 부족·과도한 외부 링크·AI 일반론 여부를 검사.
- `moderation_review`: 신규·미검증·위험 신호가 있는 퍼블리셔만 Findable 운영자 검토.
- `published`: 검증된 퍼블리셔의 공개·색인 가능한 글. 발행자·작성자·측정 기준일을 명시.
- `noindex`: 신규·검증 전·정책 리스크가 있는 글에 임시 적용하는 안전장치.

Google도 신규 사용자 콘텐츠를 우선 `noindex` 처리하고 수동 승인·스팸 모니터링을 권한다.
([Prevent user-generated spam](https://developers.google.com/search/docs/monitor-debug/prevent-abuse))

## 추천 워크플로와 데이터

```text
immutable measurement snapshot
→ ContentRevision(draft)
→ publisher_review
→ quality_check
→ moderation_review(조건부)
→ PublicationJob
  ├─ published transaction
  ├─ apps/web cache invalidation
  ├─ sitemap / llms.txt refresh
  └─ ActionCompletion record
→ published | archived
```

반려는 종착 상태가 아니라 `ContentReviewEvent(returned)`로 남기고 새 revision을 만든다.
소유권은 `Publisher`를 중심으로 둔다. 고객사 퍼블리셔는 `brandId`를 통해 기존 org 스코프를
따르고, Findable 공식 퍼블리셔는 `brandId` 없이 내부 운영자 권한으로 관리한다.

## 본문·편집기

- 지금 채택: Markdown + `react-markdown` + `remark-gfm` + `rehype-sanitize`.
  `react-markdown`은 안전한 기본 렌더링을 지향하며 허용 범위 고정에 sanitizer 사용을 권장한다
  ([공식 GitHub](https://github.com/remarkjs/react-markdown)).
- 금지: AI·고객 제공 MDX. JSX·표현식 평가 경계가 생긴다.
- v2 후보: TipTap, Lexical, Plate. TipTap은 headless 오픈소스 editor지만 collaboration/comments 등의
  고급 기능은 유료 기능이 섞여 있어 MVP에는 과하다([공식 사이트](https://tiptap.dev)).

## MVP 완료 기준

- 공개 조회는 `published AND publishedAt <= now()`만 반환.
- 고객은 자기 퍼블리셔의 draft·review·published 콘텐츠만 접근.
- 검증된 퍼블리셔는 품질 검사를 통과한 글을 발행할 수 있고, 신규·위험 퍼블리셔는 moderation을 거친다.
- revision에 evidence·metrics·측정 시각·모델/프롬프트 버전을 불변 저장.
- PublicationJob은 캐시·sitemap·llms.txt·ActionCompletion 실패를 재시도 가능하게 기록.
