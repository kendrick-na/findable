## 2. 핵심 아키텍처 결정 — CMS를 새로 만드는가, BaseHub를 쓰는가

### 결정: **새 DB 모델(Prisma)로 간다. BaseHub 재사용 안 함.**

| 이유 | 설명 |
|---|---|
| 🔴 소유권 축이 다르다 | BaseHub는 Findable 운영자가 편집하는 CMS다. 이 플랫폼은 Findable과 고객사가 각각 발행자가 되는 구조라 **Publisher별 소유·승인·공개 발행 상태**가 필요하다. 고객사 퍼블리셔는 기존 `Brand → Organization` 스코프를 타야 하므로, BaseHub에 권한 모델을 얹는 것보다 `packages/database`(Prisma+Neon) 축에 맞추는 게 정합적이다 |
| 🔴 승인 게이트가 워크플로다 | "AI 초안 → 대기 → 승인/거절 → 발행"은 상태 머신이다. BaseHub는 콘텐츠 저장소일 뿐 이런 워크플로 상태를 자연스럽게 못 표현한다. Prisma는 이미 `AuditJob.status`(queued/processing/completed) 같은 상태 필드 패턴이 있다 — 같은 패턴 재사용 |
| 🔴 GEO 액션과의 연결 | 콘텐츠 초안이 어떤 `GeoAction`(evidence·kind·target)에서 나왔는지 FK로 물어야 한다. BaseHub 콘텐츠와 우리 DB의 액션을 양쪽에서 동기화하면 정합성이 갈린다(이 저장소 최다 사고 패턴 — "같은 값을 두 벌로 세면 화면과 저장이 갈린다") |
| Findable 자체 인사이트는? | 이것도 **같은 모델에서 `Publisher.kind=findable`로 구분**한다. 별도 CMS 두 개를 유지하는 비용보다 하나의 모델 안에서 발행자 축만 나누는 게 싸다 |

⚠️ BaseHub 자체를 폐기하는 게 아니다 — 지금 있는 마케팅 페이지(랜딩 등)에 쓰이고 있다면
그건 그대로 두고, **블로그만** 새 모델로 간다(`apps/web/app/[locale]/blog/page.tsx`의
"BASEHUB feed 미설정" 주석이 이미 미사용 상태였다는 뜻이라 전환 비용 0).

### 2-b. 외부 벤치마크 보정 — 새 CMS가 아니라 워크플로를 채택한다

Payload·Apostrophe 등은 draft·revision·작성자/편집자 권한 분리·preview·발행 작업을 기본
패턴으로 둔다. 하지만 Payload의 Postgres 계층은 Drizzle라 현재 Prisma·Clerk·측정 데이터와
중복된다. **따라서 CMS는 도입하지 않고, 다음 최소 모델을 Prisma에 직접 둔다.**

- `Publisher`: Findable 공식 계정 또는 고객사 브랜드 계정. 공개 프로필·slug·검증 상태를 가진다.
- `Content`: 현재 공개 상태, slug, publisherId, sourceActionKind/sourceActionTarget.
- `ContentRevision`: 제목·Markdown 본문·생성 프롬프트/모델·측정 evidence/metrics의 불변 스냅샷.
- `ContentReviewEvent`: 퍼블리셔 제출·승인·반려·운영자 moderation을 append-only 기록.
- `ContentQualityCheck`: 중복·키워드 반복·출처 부족·링크 남용·AI 일반론 여부를 기록.
- `PublicationJob`: published 전환, apps/web 캐시, sitemap·llms.txt, ActionCompletion을 재시도 가능하게 조정.

`organizationId`는 고객사 콘텐츠에 중복 저장하지 않는다. 고객사 `Publisher`는 `brandId`를 통해
`brand.organizationId` 관계로 조직을 스코프한다. `GeoAction`은 매 측정마다 재생성되는 계산값이므로
FK가 아니며, 생성 시점의 측정 스냅샷을 revision에 저장하는 것이 출처 보존 방식이다.

고객사 글도 공개·색인 발행 대상이다. 다만 포지셔닝은 "Findable 도메인 권위 대여"가 아니라
**진단 데이터 기반의 퍼블리셔 네트워크**여야 한다. 신규·미검증·품질 위험이 있는 퍼블리셔만
임시 `noindex` 또는 운영자 moderation으로 보내고, 검증된 퍼블리셔의 고유 데이터 기반 글은
정상적으로 공개·색인한다.

## 3. 데이터 모델 (초안 — 승인 후 schema.prisma 반영)

```prisma
enum PublisherKind {
  findable  // Findable 공식 퍼블리셔
  brand     // 고객사 브랜드 퍼블리셔
}

enum ContentStatus {
  draft              // AI 생성 또는 직접 작성, 아직 제출 전
  publisher_review   // 퍼블리셔 검토·수정·승인 대기
  quality_check      // 자동 품질·정책 검사
  moderation_review  // 신규·미검증·위험 퍼블리셔만 운영자 검토
  published          // 라이브
  archived           // 발행 후 내려짐
}

model Publisher {
  id          String        @id @default(uuid())
  kind        PublisherKind
  slug        String        @unique
  name        String
  description String?
  websiteUrl  String?

  // brand 타입일 때만 값. findable 타입은 null(운영자 소유).
  brandId String? @unique
  brand   Brand?  @relation(fields: [brandId], references: [id], onDelete: Cascade)

  verifiedAt  DateTime?
  suspendedAt DateTime?

  contents Content[]

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}

model Content {
  id             String            @id @default(uuid())
  publisherId    String
  publisher      Publisher         @relation(fields: [publisherId], references: [id], onDelete: Cascade)

  // 이 글이 어떤 GEO 액션에서 나왔는지 — 근거 추적(actions.ts의 GeoAction과 매칭).
  //   ActionCompletion과 같은 키 축(kind+target)을 쓴다(중복 모델링 금지).
  sourceActionKind   String?
  sourceActionTarget String?

  locale   String   // "ko" | "en" — apps/web [locale]과 동일 축
  slug     String
  title    String
  // 본문은 Markdown 텍스트로 저장(BaseHub 대신 Prisma Text 컬럼 — 콘텐츠 규모가
  //   블로그 글 수준이라 별도 오브젝트 스토리지 없이도 감당 가능. 후일 방대해지면
  //   Vercel Blob으로 옮기되 지금은 과설계 금지).
  bodyMarkdown String @db.Text
  excerpt  String?  // 목록·OG용 요약. 없으면 본문 앞부분에서 자동 생성.

  status      ContentStatus @default(draft)
  publishedAt DateTime?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@unique([publisherId, locale, slug])
  @@index([publisherId])
  @@index([status])
}
```

**왜 이렇게 좁혔나 (과설계 방지)**:
- 태그·콘텐츠 유형·시리즈는 **공식 리서치 1호와 기존 공개 연구 자산을 한 허브로 통합하는
  시점에 도입한다.** 초기 스키마에는 넣지 않았으나, 공개 허브의 검색·섹션과 CMS의 검색
  미리보기가 실제 요구가 된 2차 구현에서 `contentType`, `series`, `tags`, 대표 이미지,
  SEO 메타데이터를 추가했다.
- 댓글·좋아요 같은 인터랙션은 서브스택 문서의 "❌ 훔치면 독"(Notes식 SNS 피드, 콜드스타트
  가혹)에 해당 — 넣지 않는다.

## 4. 반자동 파이프라인 — 실제 흐름

```
① 측정 완료(기존 cron/수동 측정)
    ↓
② buildGeoActions() 가 content_fix 킨드 액션 생성(이미 있음, 안 건드림)
    ↓
③ 🆕 콘텐츠 초안 생성 — content_fix와 그 시점의 측정 evidence·metrics를 고정해 AI가
    **안전한 Markdown revision** 작성 → Content(status=draft) 저장
    ↓
④ 🆕 퍼블리셔 검토 대기 화면에 뜬다(status=publisher_review)
    │
    ├─ brand 퍼블리셔 → 고객사가 직접 편집·승인
    └─ findable 퍼블리셔 → Findable 운영자가 직접 편집·승인
    ↓
⑤ 자동 품질 검사(status=quality_check)
    ├─ 통과 + verified publisher → 발행 job
    └─ 신규·미검증·위험 신호 → moderation_review
    ↓
⑥ PublicationJob이 published 처리·sitemap/llms.txt 발견·ActionCompletion 기록을 조정
    반려는 상태 종착점이 아니라 review event로 기록하고 새 revision을 만든다.
```

⚠️ **"고객 승인=항상 즉시 발행"은 아니다**. 검증된 퍼블리셔는 품질 검사 통과 후 바로 발행할 수
있지만, 신규·미검증·위험 신호가 있는 경우 Findable 운영자 moderation을 거친다. 이 차이가 있어야
SEO/GEO 최적화 실행 플랫폼이면서도 대량 자동발행 리스크를 피한다.

## 5. SEO/GEO 최적화 요건 (`seo-ux.md` 그대로 적용, 재리서치 안 함)

| 요건 | 적용 |
|---|---|
| 🔴 SSR 필수(크롤러가 JS 안 읽음) | 블로그 상세는 Next.js 서버 컴포넌트로 sanitize된 Markdown을 서버에서 렌더 — 클라이언트 하이드레이션 후에만 본문이 뜨는 구조 금지 |
| h1에 주제 명시 | `title` 필드가 곧 h1. 빈 제목 발행 차단(승인 화면에서 필수 필드) |
| 운영자 정보 노출 | brand 타입 글은 **어느 브랜드가 발행했는지 명시**(익명 발행 금지 — E-E-A-T 판정 사유) |
| 화면에 없는 내용 마크업 금지 | 구조화 데이터(JSON-LD)는 실제 렌더된 title·본문만 반영 |
| 분량 ≠ 순위 | AI 초안 생성 시 "길게 써라" 같은 프롬프트 지시 금지 — 근거(evidence) 밀도가 기준 |
| ⛔ 키워드 반복·자체 생성 별점 | 프롬프트 가드레일에 명시 금지 |

**GEO 특화(§0-a 리서치 재확인)**: "고유 데이터·통계"가 인용 예측변수 1위였다 → AI 초안 프롬프트는
**반드시 그 브랜드의 실측 데이터(트래킹 점유율·순위 변화)를 본문에 인용 형태로 포함**시킨다.
일반론만 쓴 글(경쟁사도 다 쓸 수 있는 문장)은 승인 화면에서 "고유성 낮음" 경고를 낸다(향후,
1차 버전은 사람이 눈으로 판단 — 자동 판정 로직은 과설계).

## 8. 이 설계로도 안 고쳐지는 것 (강제 3개)

1. **"고유 데이터"의 진짜 밀도는 측정 못 함** — AI 초안이 브랜드 실측 수치를 인용해도, 그게
   "AI 검색이 실제로 인용할 만큼 고유한가"는 사람 판단에 의존한다. 자동 고유성 점수는 1차 버전에 없다.
2. **콘텐츠 0건 콜드스타트** — 서브스택 문서가 경고한 "Notes 피드 유령도시" 리스크의 축소판이
   블로그에도 있다. Findable 자체 인사이트를 먼저 채워야 브랜드 콘텐츠가 나왔을 때 플랫폼이
   빈 곳처럼 안 보인다(순서: Findable 글 먼저, 고객 콘텐츠는 그 다음 유도).
3. **네이버 등 국내 검색엔진의 AI 자동생성 판정 기준은 외부에 공개돼 있지 않다** — "5~8주 후
   누락"이라는 리서치 수치는 실측 사례고, Findable 자체 콘텐츠가 같은 리스크를 피하는지는
   발행 후에만 확인 가능하다(선제 방어는 §5 가드레일이 최선).

## 9. 개발 순서 및 구현 결과

1. **Prisma 스키마 반영**(`Publisher`·`Content`·`ContentRevision`·`ContentReviewEvent`·`ContentQualityCheck`·`PublicationJob`) → migrate → tsc
2. **AI 초안 생성 서버 로직** — `content_fix` + 측정 스냅샷 → 안전한 Markdown revision
3. **인사이트 탭 최적화 실행 화면**(`apps/app`) — 액션가이드에서 글 초안 생성·편집·승인까지 연결
4. **품질 검사·moderation·발행 작업** — 상태 전환, 동적 sitemap·llms.txt, ActionCompletion, 실패 원문 보존·재승인 처리
5. **공개 피드·퍼블리셔 홈·상세 재배선**(`apps/web`) — BaseHub 참조 제거, published Content만 조회
6. **발행 후 SEO/GEO 검증** — `seo-ux.md` 체크리스트 + 실제 크롤러 시뮬레이션(GPTBot 등 JS 미실행
   전제로 SSR 응답 확인)

각 단계마다 tsc·테스트·Storybook 눈확인 사이클(이 세션에서 이미 3번 반복한 패턴) 유지.

### 9-a. 1차 구현 결과 (2026-08-22)

- DB: `Publisher`, `Content`, `ContentRevision`, `ContentReviewEvent`,
  `ContentQualityCheck`, `PublicationJob` 및 additive migration 작성·Prisma client 생성.
- 생성: 최신 `content_fix`와 측정 스냅샷으로 Markdown 초안 생성. 모델 장애 시에도 근거 기반

- 고객 화면: `/insights` → 초안 생성 → `/insights/[contentId]` 편집·승인 → 품질 검사.
- 운영 화면: `/admin/content`에서 신규/경고 퍼블리셔 검수, Findable 공식 리서치 초안 생성.

- 재측정 연결: 발행 시 `ActionCompletion`에 SoV·인지율 스냅샷을 남기고 추세 `Annotation`에

### 9-b. DB 적용·스모크 결과 (2026-08-22)

- 연결된 Neon DB에 `20260822_content_platform` migration 적용 완료.

### 9-e. 퍼블리싱 성장 루프 3차 구현 (2026-08-22)

- 예약 발행: 편집기에서 브라우저 시간대 기준 발행 시각을 정한다. 품질 검사와 운영 검수를
  통과한 글만 `scheduled` 상태가 되며, 보안 크론이 due job을 선점해 멱등 발행한다. 현재 Vercel
  Hobby 운영 배포는 하루 1회(03:00 KST) 제한이며, Pro 전환 시 `*/15 * * * *`로 바꾸면 된다.
- 뉴스레터: 퍼블리셔별 사용 여부, 공개 구독 폼, 이메일 이중 확인, 발행 캠페인·수신자별 전송
  이력, 서명 토큰 기반 POST 수신거부를 구현했다. 글이 실제 공개된 뒤에만 캠페인이 대기열에
  들어가며 Resend 미설정 환경에서는 발송을 실행하지 않는다.
- 고객 전용 도메인: `/insights/settings`에서 도메인을 입력하고 `_findable` TXT로 소유권을
  확인한다. Vercel 프로젝트 도메인 연결 키가 있으면 자동 연결하고, 공개 호스트는 검증된
  Publisher를 DB에서 다시 확인한 뒤 전용 홈·글·canonical·robots·sitemap을 제공한다.
- 성과 측정: 발행을 SEO/GEO 점수 상승으로 간주하지 않는다. 대시보드에서 콘텐츠 최적화
  준비도, 색인 가능 여부, 사이트맵 포함, 발행 전후의 사용 가능한 AuditJob 점수, 발행 URL의
  실제 AI 인용 감지를 서로 다른 지표로 표시한다. Google/Naver 실제 색인 확인은 Search
  Console 연결 전까지 주장하지 않는다.
