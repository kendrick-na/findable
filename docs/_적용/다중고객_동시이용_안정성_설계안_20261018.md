# 다중 고객 동시 이용 안정성 설계안 (구현 전 · 읽기 전용 점검 · 대표 승인 대기)

작성: 측정 준비도 게이트 개발 세션, 2026-10-18. 대표 질문: **"B2B 고객사 A·B·C가 동시에 쓰는 상황에서 멈추거나 엔진 오류가 나서는 안 된다."**
방법: 코드 읽기만(운영 호출·DB 쓰기 없음). 코드로 확인한 것은 근거 파일을, 못 한 것은 **[확인필요]** 로 표시. 앞의 「'측정 못 함' 줄이기 설계안」(재시도 칸당 2회·빈 응답 처리·속도 조절·시작 전 점검)은 이 문서에 **통합**했다(5절).

## 0. 한 줄 결론

**기초 안전장치(중복 실행 방지·질문 단위 저장·이어가기·원가 장부)는 이미 탄탄하다. 비어 있는 것은 "여럿이 동시에 쓸 때" 필요한 4가지다: ① 전체 동시 실행 상한과 공정한 대기 줄, ② 엔진별 공유 속도 조절과 서킷브레이커, ③ 429·빈 응답·중단 작업의 자동 복구, ④ 고객별 비용 상한과 운영자 알림.** 새 화면은 필요 없다(기존 "측정 중·이어가기 대기·반영 예정·제외 엔진" 표현을 재사용). 발송(10/20) 전에는 **읽기 점검·알림 규칙**만, 코드 변경은 발송 후 약 2~3주(4단계, 단계마다 대표 승인).

| S28 | 한 고객 오류가 다른 고객에 번짐 | 회차마다 독립 실행·독립 저장. 공유되는 것은 공급자 키·한도·Letsur 차단기(인스턴스별) | — | 🟡 | S1·S6·S10으로 공유 자원을 보호 | 위 항목에 포함 |

## 3. 설계 원칙

1. **못 잰 것을 0이나 '미노출'로 세지 않는다.** 재시도 후에도 못 재면 분모에서 빼고 사유를 기록(검색 결과가 정말 0건인 것처럼 사실로 확인된 것만 예외).
2. **애초에 못 잴 일을 만들지 않는다.** 시작 전 점검(키·잔량·엔진 상태·DB·사이트 읽기) → 못 쓰는 것은 미리 제외하고 기록.
3. **공유 자원은 공정하게 나눈다.** 전체 동시 실행 상한 + 고객별 상한 + 오래 기다린 고객 우선.
4. **한 엔진의 문제를 그 엔진에서 끝낸다.** 서킷브레이커로 격리하고 나머지로 진행.
5. **재시도는 반드시 상한이 있다.** 칸당 2회, 회차당 총량, 간격 지터·Retry-After 준수.
6. **끊겨도 이어서 한다(멱등).** 질문 단위 저장·원장 기록을 그대로 쓰고, 중단 작업은 남은 질문만 자동 이어가기.
7. **고객별 비용 상한을 둔다.** 플랜별 일일 측정 횟수·원가 상한, 전역 일일 예산은 유지.
8. **상태는 기존 표현으로 보여 준다.** 새 화면 없음.
9. **운영자는 사람이 보기 전에 알림을 받는다.** 로그가 아니라 알림(6절).
10. **장애 훈련을 한다.** 가짜 엔진 장애·급증 부하를 시험 환경에서 재현(5절 4단계).

### 상태 표시 매핑 (새 화면 없이)
| 상황 | 고객 화면에 쓰는 기존 표현 |
|---|---|
| 대기 줄에서 기다리는 중 | 기존 "측정 대기(queued)" 표시 — 단 지금은 30분 넘으면 실패 처리라 **대기 줄용 별도 만료 기준** 필요([확인필요] 현재 화면 문구) |
| 마감으로 일부 질문이 남음 | "이어가기 대기"(이미 있음) |
| 늦은 답을 기다리거나 재시도 중인 칸 | "반영 예정"(이미 있음) |
| 엔진이 격리되어 제외됨 | "이번 회차 제외 엔진: X"(측정 못 한 엔진 표시와 같은 자리) |
| 측정 한도 도달 | 기존 `rate_limited` 안내 |
새 문구가 꼭 필요하면 **구현 전에 시안을 보여 승인**받는다.

## 4. 통합 설계 구조 (구성요소 6개)

| 구성요소 | 역할 | 기존 재사용 | 새로 필요 |
|---|---|---|---|
| ① 입장 관리 + 공정 큐 | 전역·고객별 동시 실행 상한, 대기 줄, 오래 기다린 고객 우선 | `claimAuditExecution`(선점), 이어가기 대기 상태 | 실행 중 수를 세는 조회(`processing` + 유효 lease), 대기 줄 처리 cron(1~2분 간격) |
| ② 엔진 건강 관리 | 서킷브레이커(격리·복귀), 엔진별 공유 속도 조절 | `packages/rate-limit`(Upstash) [활성 확인필요], Letsur 차단기 개념 | 공유 상태 저장(Redis 우선, 없으면 작은 DB 표 1개 — 별도 승인) |
| ③ 재시도 정책 | 칸당 2회·지터·Retry-After, 빈 응답 오류화, 검색 API 1회 재시도 | `late-cells`(다시 묻기 회차) | 인라인 재시도(회차 없는 실행용) + 칸 시도 횟수 기록 |
| ④ 중단 복구 | 배포·급사로 멈춘 작업을 남은 질문만 자동 이어가기 | 질문 단위 checkpoint, 원장, 이어가기 | stale 정리가 "실패"로 닫기 전에 진행 있는 작업은 이어가기 대기로 전환 |
| ⑤ 비용 상한 | 고객별 일일 측정 횟수·원가 | 무료 전역 예산, `retry-policy` | 플랜별 상한 값(대표 결정), 초과 안내 |
| ⑥ 알림·점검 | 임계 알림, cron 하트비트, 일일 요약 | Sentry `captureOpsAlert` | 알림 규칙 표(6절)를 코드로 |

### 입장 관리 동작(제안)
1. 측정 시작 요청 → 시작 전 점검(키·잔량·엔진·DB) 통과 확인.
2. 실행 중 수가 전역 상한 미만이고 이 고객 상한 미만이면 **즉시 시작**(지금과 같은 체감).
3. 아니면 `queued + 대기 시각`으로 두고 응답은 "대기 중". 처리 cron(1~2분)이 **오래 기다린 고객 순**으로 상한 안에서 시작.
4. 대기가 길어지면(예: 10분) 운영자 알림. 대기 만료(예: 30분)는 실패가 아니라 "계속 대기"로 둔다 — 단 대표 승인 필요.
5. **상한 값은 공급자 실제 한도 확인 후** 정한다(초기 제안: 전역 8, 고객별 2 — 임의값이라 [확인필요]).

## 9. 확인하지 못한 것 (전부 읽기 전용 점검 대상)
- 공급자(Letsur·Gateway 각 모델)의 실제 분당·동시 호출 한도, 렛서 유닛 잔량 확인 방법·경보 유무.
