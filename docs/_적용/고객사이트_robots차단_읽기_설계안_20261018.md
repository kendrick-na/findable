# ⑧ 고객이 등록한 사이트의 robots 차단 읽기 — 설계안 (구현 전 · 대표 승인 대기)

작성: 측정 준비도 게이트 개발 세션, 2026-10-18. 입력: 관제탑 전달 대표 결정(소유자 인증 단계 없음, 고객 등록 사이트는 robots를 무시하고 읽음, 제3자 사이트는 robots 존중 유지) + 조사 문서 `robots차단_고객사이트_읽기_조사_20261018.md`. **코드 변경 없음.**

## 0. 한 줄 결론

**읽는 사람이 "누구의 사이트인가"를 코드에서 분명히 나눈다: ① 고객이 Findable에 등록한 자기 사이트 → robots 차단을 무시하고 읽는다, ② 동의 없는 제3자(KAIST 52곳 익명 시험 같은 도구) → 지금처럼 robots를 지킨다.** 정상 사이트의 화면·결과는 바뀌지 않고, 읽기가 막힌 **고객 사이트에서만** 안내 한 줄이 생긴다. 소유자 인증 화면은 만들지 않는다. 구현은 약 3~4일(화면 시안 승인 대기 시간 제외).

| 항목 | 현재 |

## 2. 설계

### 2-1. "누구의 사이트인가" 구분 — 코드에 명확히
- `readSiteProfile(domain, { audience })`에 **`audience: "registered_customer" | "third_party"`** 를 추가한다. **기본값은 `third_party`(지금처럼 robots 존중)** — 값을 안 넘기는 호출은 전부 예전과 같다.
- `registered_customer`는 **고객 조직에 등록된 브랜드를 읽는 호출만** 넘긴다(질문 제안·미리 돌려 보기·고객 측정). 영업용 내부 조직·KAIST 52곳 같은 익명 시험 측정·영업 메일 수집은 넘기지 않는다.
- robots 무시는 플래그 `SITE_READ_CUSTOMER_ROBOTS_IGNORE_ENABLED`(기본 꺼짐) 뒤에 둔다. 켜지기 전에는 동작이 변하지 않는다.
- robots를 무시하고 읽었다는 사실은 **로그에 남긴다**(어느 도메인·어느 조직·언제) — 나중에 "왜 읽었나"에 답하는 기록.

### 2-2. 우리 봇 이름을 콕 집어 막은 경우도 무시한다 (대표 결정 2026-10-18)
고객이 Findable에 등록한 사이트는 `User-agent: *` 전체 차단뿐 아니라 **`User-agent: FindableBot` + `Disallow: /`(우리 봇 이름 지정 차단)도 무시하고 읽는다.** 대표 판단: 고객이 우리 서비스에 등록한 이상 "읽고 측정하고 해결해 주는" 것이 서비스이므로 robots는 읽기를 막는 근거가 되지 않는다. 구분은 오직 **누구의 사이트인가(audience)** 다 — 등록 고객 사이트는 무시, 동의 없는 제3자 사이트는 어떤 robots 줄이든 **계속 존중**한다. (이 구분이 코드에서 섞이지 않도록 `audience` 값은 호출부가 명시해야 하고, 기본값은 존중이다.)
- 남는 위험(대표가 알고 선택): 고객이 의도적으로 우리 봇을 막았는데도 읽는 경우의 분쟁 가능성. 완화책은 로그(무시하고 읽은 기록)와 약관 한 줄(법무 확인).

### 2-3. 읽기 성공을 높이는 기술 (정직한 방식만)
| 항목 | 내용 | 새 패키지 |
|---|---|---|
| 봇 이름 | `FindableBot/1.0` + 우리 소개 페이지 주소. 기존 허용 목록이 깨지지 않게 **옛 이름(`FindableMeasurementBot`)도 문자열에 함께** 둔다 | 없음 |
| 큰 페이지·타임아웃 | ①에서 완료(앞 500KB 스트림 읽기, 단계별 시간 제한) | 없음 |
| JS로 그리는 사이트 | 이미 있는 렌더링(`SITE_RENDER_ENABLED`). 운영은 켜져 있음. 고객 사이트는 robots 무시 정책을 렌더링에도 같이 적용. 로컬·측정은 운영과 같은 설정으로 맞추는 것은 ②에서 로그로 드러내도록 함 | 없음 |
| robots 아닌 403 차단(Cloudflare·방화벽) | 같은 요청을 **봇 이름 그대로** 한 번 재시도(www↔apex 포함)까지만. 그래도 막히면 "차단"으로 기록하고 안내(3절) | 없음 |
| 읽기 결과에 "왜 못 읽었나" 기록 | `readSiteProfile`이 null만 주던 것을, 이유(robots 전체 차단·방화벽 403·인증서 오류·접속 불가·너무 느림)를 함께 돌려주는 **상세 버전**을 추가(기존 함수는 그대로 유지) | 없음 |

### 2-4. 하지 않는 것 (대표 지시 4번 그대로)
구글봇 등 타사 봇 사칭, 주거용 프록시, 캡차 자동 풀이, **인증서 검증 끄기**(인증서 오류 사이트는 안내 + 직접 입력으로 처리). Web Bot Auth(요청 서명)·외부 렌더링 서비스는 **2단계**(별도 승인).

### 2-5. 약관 한 줄 (법무 확인 필요)
"Findable에 사이트를 등록하면, 서비스 제공(질문 제안·측정·점검) 목적으로 FindableBot이 robots.txt 제한과 관계없이 해당 사이트의 공개 페이지를 읽는 데 동의한 것으로 봅니다." — **초안일 뿐, 법무 확인 전에는 약관에 넣지 않는다.** (등록 화면에 동의 체크칸을 새로 만들지는 않는다. 화면 변화 0)

## 3. 화면 변화 — 최소안

| 상황 | 화면 |
|---|---|
| 정상 사이트(예: 100곳 중 95곳) | **변화 0** (문구·위치·결과 동일) |
| robots를 무시하고 읽는 데 성공한 고객 사이트 | **변화 0** (읽기가 되므로 안내 없음) |
| 읽기가 끝내 실패한 **고객 등록 사이트만** | 질문 제안·준비도 안내 영역에 **한 줄** + 접이식 "자세히" |
| 비고객·내부 도구 | 화면 없음 |

시안(구현 전 대표 승인용 문구 후보, 위치는 기존 "사이트 글자가 적어요" 안내 자리):
1. 방화벽 차단: "사이트가 자동 읽기를 막고 있어요. **FindableBot** 을 허용하면 더 정확해져요. 지금은 한 줄 소개로 대신할 수 있어요. [자세히]"
2. 인증서 오류: "사이트 보안 인증서에 문제가 있어 읽지 못했어요. 인증서를 고치면 읽을 수 있어요. 지금은 한 줄 소개로 대신할 수 있어요."
3. (robots가 아니라 방화벽·서버 설정이 막는 경우만 해당 — robots 차단은 무시하고 읽으므로 이 안내는 읽기가 끝내 실패했을 때만 나온다.)
- "자세히"(접이식): Cloudflare(WAF 규칙 Skip, Bot Fight Mode 예외)·Vercel(Firewall Bypass)·robots 한 줄 예시 + **GPTBot(학습용)과 OAI-SearchBot(검색 인용용) 구분**. 이 안내는 곧 GEO 처방("AI 검색 봇을 막고 있으면 AI 답변에 인용되기 어렵다")이므로 점검 결과의 발견으로도 쓸 수 있다.
- 새 입력칸·새 단계는 만들지 않는다. 대체 수단은 **기존 "한 줄 소개" 입력**을 그대로 쓴다(사이트 주소·sitemap 직접 입력 칸은 1단계에서 만들지 않음).

## 4. 일정·규모

| 단계 | 내용 | 규모 | 승인 |
|---|---|---|---|
| 8-a | `audience` 구분 + 고객 사이트 robots 무시(플래그 뒤) + 로그 + 봇 이름 정리 + 읽기 실패 이유 상세 버전 + 테스트 | 1.5일 | 구현 승인 |
| 8-b | 봇 소개 페이지(`/ko/bot` 한 장, 정적) — UA의 안내 주소 | 0.5일 | 문구 승인 |
| 8-c | 고객 사이트 한 줄 안내 + 접이식 도움말 | 1일 | **시안 승인 후** |
| 8-d | 약관 한 줄 | 법무 확인 후 | 대표 |
| 2단계 | Web Bot Auth 서명, 외부 렌더링 서비스, 고정 IP | 각 2~3일 | 별도 승인 |

**합계 약 3일(8-c 시안 승인 대기 제외).** 질문 생성 쪽 ③⑥⑨는 이미 플래그 뒤에서 완료(별도 보고).

## 5. 테스트 계획
- `audience` 기본값(third_party)에서 robots 차단(전체 차단·봇 이름 지정 차단 모두) 시 예전과 똑같이 null — **회귀 테스트**(영업 메일 수집·익명 측정 경로 포함 호출처 목록 검사).
- 고객 + 플래그 켜짐: `User-agent: *` 전체 차단도, `User-agent: FindableBot` 명시 차단도 무시하고 읽는다(제3자는 둘 다 존중).
- 상세 결과: robots·403·인증서·타임아웃을 각각 구분해 돌려주는지(가짜 응답).
- 정상 사이트: 읽기 결과가 이번 변경 전후 **같다**(가짜 응답으로 동일 프로필).
- 로그: 무시하고 읽은 경우 도메인·조직이 남고 개인정보는 안 남는다.

## 7. 확인하지 못한 것
- Cloudflare·Vercel·고도몰 등 각 서비스의 설정 화면 이름과 경로는 조사 문서의 `[확인필요]`를 그대로 따른다. 구현 때 공식 문서로 다시 확인한다.
- 고객 측정 경로(러너)가 어떤 읽기 함수를 거치는지 전수 호출처 확인은 8-a 착수 때 한다(여기서는 `readSiteProfile` 호출처 2곳만 확인).
- robots를 무시하는 방식이 고객·제3자 분쟁에서 어떻게 평가될지는 법률 자문이 아니다. 법무 확인 필요.
