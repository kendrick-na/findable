> 배경: 파트너 승인 기능을 만들다 보니 `insider`가 실혜택이 없고, 게이팅축(plan.ts)과 결제축(DB Plan)이 **따로 놀아** 이코노미 재설계가 필요해짐.

## 0. 핵심 결론 (3줄)
1. **이미 진짜 요금제가 있다** = web pricing/checkout의 4-tier(Free/Starter/Growth/Scale/Enterprise), DB `Plan` enum과 일치. 카테고리 표준(프롬프트·브랜드 게이팅)과도 맞음.
2. **`insider`/`pro`는 유령 어휘** — plan.ts에만 있고 결제와 무관. 게이팅축을 **결제축으로 통일**한다.
3. **파트너 = 베타/얼리 유저** — 별도 tier가 아니라 **"Growth 상당 기능 + 영구 혜택 + Founding 배지"를 승인으로 부여하는 grant**. 정의는 유동적으로 열어둠.

## 1. 현재 모순 (실측)

### 있는 것 A — 결제축 (진짜 요금제, web + DB)
`DB Plan enum` = `free / starter / growth / scale / enterprise` ↔ web pricing 4-tier와 1:1.

| tier | 월 가격 | 추적 프롬프트 | 브랜드 | 대상 |
|------|--------|-------------|--------|------|
| Free | ₩0 | 무료 진단(1회) | 1 | 진입 |
| Starter | ₩99,000 | 30 | 1 | 1인 창업자·개인 브랜드 |
| Growth | ₩390,000 | 150 | 5 | 스타트업·SMB (추천) |
| Scale | ₩990,000 | 500 | 무제한 | 미드마켓·D2C |
| Enterprise | 맞춤(연 ₩30M~) | 맞춤 | 맞춤 | F500 Korea |

### 있는 것 B — 게이팅축 (유령, 앱에만)
`plan.ts Plan` = `free / insider / pro / enterprise`. 앱 잠금은 전부 `isPaid()`=**pro 이상** 기준.
- 경쟁사 비교·추적 알림·Export → `pro` 잠금.
- **문제**: insider(1) < pro(2) → 승인 파트너가 아무것도 못 엶. + starter/growth/scale과 매핑 안 됨.

### 결론
**A(결제축)가 진실. B의 insider/pro를 폐기하고 starter/growth/scale로 게이팅을 정렬.** enterprise는 양쪽 공통이라 유지.

## 2. 카테고리 표준 (GEO SaaS 리서치, 2026)

**모두가 게이팅하는 4개 축** (경쟁사 Peec·Profound·Otterly·Scrunch·Semrush 실측):
1. **프롬프트 수** — #1 보편 미터 (15→50→100→350→500+). Findable도 이미 이걸로 나눔 ✅
2. **AI 엔진 수** — 2위 레버. 저가=ChatGPT/4개 코어, 상위=Gemini·Claude·Grok 등 해금. (Profound 1→3→10이 가장 선명) ← **Findable 미적용, 훔칠 후보**
3. **브랜드/도메인/프로젝트 수** — 1→5→무제한. Findable 이미 적용 ✅
4. **갱신 주기** — 주간(저가) vs 일간(상위). ← **Findable 미적용, 추가 후보**

**부차 게이트**: 경쟁사 추적 수·Export/API·히스토리 보존·시트 수(요즘 무제한 추세)·SSO/화이트라벨(enterprise).

**베타/파운딩 프로그램 통설**: 무료 영구 tier는 카테고리에서 지속 불가(멀티엔진 비용). 대신
- **영구 할인 lock-in**(가장 강력한 훅) + **상향된 쿼터**(현금보다 싸고 헤비유저화) + **Founding Partner 배지**(사회적 증명).
- 프레이밍 = "피드백·사례연구 대가로 얼리 액세스." ← Findable 파트너에 정확히 부합.
- ⚠️ 'Findable AI'라는 **동명 무관 Gumroad 상품**(얼리어답터 $99) 발견 → 브랜드 충돌 여부 확인 필요.

## 3. 설계안 — 결제축 통일 + 파트너 grant

### 3-A. 등급 정의 (게이팅축 = 결제축)
`plan.ts`를 `free / starter / growth / scale / enterprise` 로 교체. 위계:
```
free(0) < starter(1) < growth(2) < scale(3) < enterprise(4)
```

### 3-B. 기능 × 등급 오픈 매트릭스 (추천안)
> 원칙: 프롬프트·브랜드는 **양적 쿼터**(이미 있음), 기능은 **질적 게이트**. 엔진·갱신주기를 새 레버로 추가.

| 기능 / 쿼터 | Free | Starter | Growth | Scale | Enterprise |
|---|:---:|:---:|:---:|:---:|:---:|
| 무료 진단(1회) | ✅ | ✅ | ✅ | ✅ | ✅ |
| 가시성 대시보드·측정 요약 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 추적 프롬프트/월 | 진단만 | 30 | 150 | 500 | 맞춤 |
| 브랜드 수 | 1 | 1 | 5 | 무제한 | 무제한 |
| **AI 엔진 수** (신규 레버) | 3(읽기) | 4 코어 | +Gemini/Naver | 전체(10+) | 전체 |
| **갱신 주기** (신규 레버) | — | 주간 | 주간 | 일간 | 일간/실시간 |
| 경쟁사 비교 | 🔒 | 🔒 | ✅ | ✅ | ✅ |
| 추적 알림(자동 재측정) | 🔒 | 🔒 | ✅ | ✅ | ✅ |
| 리포트 Export(Notion·Docs) | 🔒 | 🔒 | ✅ | ✅ | ✅ |
| API 접근 | 🔒 | 🔒 | 🔒 | ✅ | ✅ |
| SSO·화이트라벨·전담매니저 | 🔒 | 🔒 | 🔒 | 🔒 | ✅ |

> = 현재 앱의 `pro` 잠금(비교·알림·Export)은 **Growth 이상**으로 매핑(pro≈growth). starter는 free보다 쿼터만 큰 진입 유료.

### 3-C. 파트너(베타/얼리) = grant, tier 아님
파트너 승인은 **등급을 새로 만들지 않고** 아래를 부여:
- **접근권**: Growth 상당 기능 오픈(=승인 시 `plan=growth` 부여). ← 지금 코드의 `insider` 자리를 `growth`로.
- **영구 혜택(파운딩 특전)**: GA 후에도 유지되는 할인/상향 쿼터. (초기엔 "Growth 무료 제공 + Founding 배지"로 시작 가능)
- **배지**: "Founding Partner"(또는 §4 라벨). 사회적 증명 + 상태.
- **정의 유동성**: 지금은 베타 유저. 나중에 대행사/제휴/리셀러로 확장 시 grant 내용만 조정(별도 tier 신설 없이).

→ 파트너 상태는 `PartnerApplication`(이미 만듦)이 진실, 승인 시 부여 plan만 `insider`→`growth`로 바꾸면 됨.

## 4. 라벨 문제 — "인사이더"·"insider" 교체

- **코드 식별자**(plan.ts Plan, DB 저장값)와 **화면 라벨**(PLAN_META.label)은 분리돼 있음 → 라벨만 바꾸면 로직 무영향.
- `insider`/`pro` 자체를 폐기(→ starter/growth/scale)하면 "인사이더" 배지도 자연 소멸.
- **파트너 배지 라벨 후보**: "파트너" / "공식 파트너" / "Founding Partner" / "얼리 파트너". ⬜ 사용자 결정.

## 5. 🟡 결정 필요 (코드 반영 전)
1. **게이팅축 통일** — insider/pro 폐기 → starter/growth/scale 매핑. 승인 파트너 부여 plan = **growth** 로? (§3-C)
2. **신규 레버 채택 여부** — AI 엔진 수 / 갱신 주기를 실제 게이트로 넣을지(지금 코드엔 없음). 넣으면 엔진 배열·주기 필드 필요.
3. **파트너 특전 범위** — 초기엔 "Growth 무료+배지"만? 영구 할인 lock-in은 결제 붙은 뒤?
4. **파트너 배지 라벨** (§4).
5. **동명 'Findable AI' Gumroad** 브랜드 충돌 확인.

## 6. 반영 시 작업 (결정 후)
- `plan.ts` Plan 타입·PLAN_RANK·PLAN_META를 starter/growth/scale로 재작성(hasPlan/isPaid 재정의: isPaid≈growth 이상).
- `sidebar.tsx` requiredPlan `"pro"`→`"growth"` 치환. page.tsx `isPaid` 유지(정의만 growth로).
- `decide.ts` 승인 push `plan:"insider"`→`"growth"`.
- (엔진/주기 레버 채택 시) 스키마·러너 게이팅 추가 — 범위 큼, 별도 단계.
- 검증: tsc·lint·배포.
