## 1. 지금 뭘 만들려고 하나 (한 문단)

Findable(한국 SEO/GEO 진단 플랫폼)에 **SEO/GEO 최적화 퍼블리싱 플랫폼**을 신설한다. Findable은
진단만 하는 서비스가 아니라, 진단 결과에서 나온 `content_fix` 액션을 근거로 최적화 아티클 초안을
만들고, 고객사 또는 Findable 퍼블리셔가 검토·수정·승인한 뒤 공개 발행까지 이어주는 실행 플랫폼이
된다. 공개 콘텐츠에는 Findable 공식 글과 고객사 퍼블리셔 글이 함께 존재한다.

## 2. 왜 이게 필요한가 (제품 맥락)

Findable은 지금 "AI 검색(ChatGPT·Perplexity·네이버 등)에 우리 브랜드가 얼마나 언급되는지
진단"하고 액션가이드를 주는 데서 출발한다. 이번 기능의 목적은 그 액션가이드를 넘어,
**SEO/GEO 알고리즘에 맞춘 글을 생성·검토·발행·측정하는 폐루프**를 만드는 것이다.
사용자(제품 소유자)가 정의한 제품 축:

> "고객들한테 GEO 진단만 하는 게 아니라, **뭘 해야하는지 직관적이고 이해쉽게** 알려줘야 하고,
> **실제 해야할 것 바로 해주는 에이전트**까지임." — 대상은 고객 사이트가 아니라 **Findable이
> 운영하는 자체 블로그 플랫폼**(고객 사이트를 대신 고치는 게 아니라서 권한 문제가 없음).

## 3. 🔴 제약 — 이걸 어기면 SEO/GEO에 역효과가 실측돼 있다

**완전 자동발행 금지.** 2026-07-21에 4개 서브에이전트가 독립 리서치한 결론
(`서브스택_결합_기획/서브스택_결합_전략_종합.md`):

- Google이 "scaled content abuse"를 2024년부터 스팸으로 규정, 2026.3 코어 업데이트에서
  최우선 집행 → 실제로 AI 대량 자동발행 사이트가 트래픽 50~80% 감소하거나 검색에서 제거됨
- 네이버 2026 제재 게시물 95%가 스팸/홍보성, AI 자동발행 글은 보통 5~8주 후 노출에서 빠짐
- **GEO 인용의 최강 예측변수는 "고유 데이터·통계"이지 블로그 글 개수가 아니다.** 편집 없는
  대량발행은 GEO 점수를 오히려 깎는다
- 자동발행 자체는 Byword·Cuppa·AirOps 등이 이미 커머디티화한 레드오션

→ 리서치 결론: **"반자동(인간 승인 게이트) + 오프페이지 신호 오케스트레이션"**. 사용자도
이번 세션에서 이걸 재확인함("완전 자동이 seo geo에 안 좋다며" → 반자동 확정).

**Codex가 지킬 것**: AI는 초안과 최적화 제안까지 자동으로 만들고, 공개 발행 전에는 퍼블리셔
승인과 품질 검사를 거친다. 검증된 고객사 퍼블리셔는 품질 검사 통과 후 공개·색인 발행할 수 있고,
신규·미검증·위험 신호가 있는 퍼블리셔는 Findable 운영자 moderation으로 보낸다. "AI 초안 →
승인 없이 라이브"는 금지다. 발행은 `PublicationJob`이 상태 전환·실패 기록·완료기록을 조정하고,
공개 앱은 동적 sitemap·llms.txt에서 published 콘텐츠만 발견한다.

## 4. 아키텍처 핵심 결정 — 왜 새 DB 모델인가 (BaseHub 안 씀)

Findable에는 이미 `packages/cms`(BaseHub, 외부 헤드리스 CMS)가 있고 `apps/web/[locale]/blog/`
라우트도 있지만 **"Coming Soon" 상태로 방치**돼 있다(`page.tsx` 주석: "BASEHUB feed 미설정").

**BaseHub를 재사용하지 않기로 결정한 이유**:
1. 콘텐츠 소유권은 Findable 공식 계정과 고객사 계정을 모두 포함하는 `Publisher` 축이어야 한다.
   고객사 퍼블리셔는 기존 `Brand → Organization` 권한을 타야 하는데, BaseHub는 이 모델을 얹기 어렵다
2. "초안→대기→승인/거절→발행"은 상태 머신이다. Prisma에 이미 `AuditJob.status` 같은 상태
   패턴이 있어 같은 방식을 재사용하는 게 기존 시스템과 정합적이다
3. `GeoAction`은 매 측정마다 재생성되는 계산값이라 FK가 아니다. 콘텐츠 revision에 생성 당시
   evidence·metrics·측정 시각을 불변 스냅샷으로 저장해야 한다

**결론**: 새 Prisma 모델 `Publisher` + `Content` 계열(전문은 설계기획서 §3). BaseHub는 폐기하지
않되 이 블로그 용도로는 안 쓴다.

## 6. SEO/GEO 요건 (구현 시 반드시 지킬 것)

- 🔴 **SSR 필수** — 블로그 상세는 서버 컴포넌트로 안전한 Markdown을 서버에서 렌더. 클라이언트
  하이드레이션 후에만 본문이 뜨는 구조 금지
- AI 초안 프롬프트는 **그 브랜드의 실측 데이터(점유율·순위 변화)를 인용문 형태로 반드시 포함**
  시킨다 — "고유 데이터가 인용 예측변수 1위"라는 §3 리서치를 따른다. 일반론만 쓰면 GEO 효과 없음
- brand 타입 글은 **어느 브랜드가 썼는지 명시**(익명 발행 금지 — E-E-A-T 판정 사유)
- 키워드 반복·자체 생성 별점 금지 (`seo-ux.md` 표준 가드레일)

## 7. 데이터 모델 (설계기획서 §3 그대로, 요지만)

```
Publisher: kind(findable | brand), slug, name, brandId?, verifiedAt, suspendedAt
Content: publisherId, sourceActionKind?, sourceActionTarget?, sourceMeasuredAt, locale, slug, status
ContentRevision: title, bodyMarkdown, excerpt, sourceEvidence, sourceMetrics, generationPrompt, model, version
ContentReviewEvent: generated | edited | submitted | approved | rejected | moderation_approved | moderation_rejected | published | archived
ContentQualityCheck: checks(JSON), status(passed | warning | failed), summary
PublicationJob: queued → processing → completed | failed
상태: draft → publisher_review → quality_check → moderation_review(조건부) → published | archived
```

댓글·좋아요 같은 SNS 기능은 **안 넣는다**. 다만 공식 리서치와 기존 공개 자산을 한 허브에서
찾아야 하는 요구가 생겨 2차 버전에 콘텐츠 유형·시리즈·태그는 도입했다.

검증: app/web typecheck, app 테스트 802개, app/web production build 통과.

## 10. 구현 후 운영 결정이 필요한 것

1. 기본 초안 모델은 기존 저비용 `gpt-4o-mini`, 장애 시 deterministic evidence template이다.
   실제 발행 데이터로 품질/비용을 비교한 뒤 모델 승격 여부를 정한다.
2. 1차 자동 품질검사는 분량·근거·제목 반복·링크·소제목·출처를 본다. 의미적 고유성 판정은
   여전히 사람 검수 영역이며, 실발행 표본이 쌓인 뒤 평가셋을 만들 수 있다.
3. Findable 공식 글은 admin `/admin/content`에서 공식 초안을 만들고 같은 편집기로 발행한다.
   실제 편집 책임자와 발행 캘린더는 운영 정책으로 정해야 한다.

## 14. Ghost/Substack형 퍼블리싱 성장 루프 추가 (2026-08-22)

- 새 migration: `20260822_publishing_growth_loop`. 예약 발행, 뉴스레터 구독/캠페인/전송,
  고객 전용 도메인 상태를 additive하게 추가한다.
- 고객 CMS: 글별 예약 시각과 발행 후 뉴스레터 발송 여부를 저장한다. 예약 글도 기존
  품질 게이트와 운영 moderation을 반드시 통과한다.
- web cron: `/api/cron/content-publishing`. 현재 Vercel Hobby 제한에 맞춰 `0 18 * * *`
  (03:00 KST)이며 Pro 전환 시 `*/15 * * * *`로 올린다. `CRON_SECRET` Bearer 인증이 없으면
  fail closed한다.
- 뉴스레터: `/api/newsletter/subscribe` → 확인 메일 → `/confirm`; 발행 후 campaign cron;
  `/unsubscribe`는 링크 스캐너가 GET만 방문해도 해지되지 않도록 최종 POST 확인을 요구한다.
- 채널 설정: app `/insights/settings`. TXT 소유권 확인 후 Vercel 프로젝트 도메인 API를 통해
  연결한다. API 키가 없으면 `verified`까지만 표시하고 활성화했다고 거짓 표시하지 않는다.
- 전용 도메인: web proxy가 호스트를 내부 `/[locale]/site/[customDomain]` 경로로 rewrite하며,
  DB에서 `active`인 도메인만 홈/글을 제공한다. 해당 호스트의 canonical·robots·sitemap도
  고객 도메인 기준이다.
- 대시보드: `contentPerformance`가 발행 전/후 실측 점수, 실제 인용 감지, 색인 가능 여부,
  최적화 준비도를 분리한다. Search Console 없이 “Google 색인 완료” 또는 “점수 상승”을
  주장하지 않는다.
