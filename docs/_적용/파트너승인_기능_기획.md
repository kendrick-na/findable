## 0. 한 줄 정의
**지금 "Clerk 대시보드에서 관리자가 손으로 `publicMetadata.plan=insider` 입력"하는 파트너 승인을, 앱 안의 신청→승인 화면으로 옮긴다.**

---

## 1. 왜 하나 (배경)

- `insider` 플랜 = **"승인된 파트너에게 열리는 특별 접근 플랜"** — 이미 `plan.ts`에 정의됨(코드값·배지·게이팅 전부 준비 완료).
- 그런데 승인 경로가 **오프-앱**이다. `plan.ts` 주석 명시: *"결제 연동 전이라 승인/유료 전환은 Clerk 대시보드 > Users > Metadata > Public 에 `{ "plan": "insider" }` 수동 입력"*.
- 문제:
  1. 관리자가 Clerk 콘솔을 열어 유저를 찾고 JSON을 손으로 쳐야 함 → 느리고 오타 위험.
  2. 사용자가 **파트너가 되고 싶다는 의사표시(신청)**를 할 곳이 없음 → 관리자가 누구를 승인해야 하는지 모름.
  3. 승인 이력·사유·감사 로그가 남지 않음.

---

## 2. 범위 (이번 단계)

**✅ 이번 단계 = 기획 확정 + 이후 "신청 + 승인 풀세트" 구현 목표**

| # | 조각 | 이번 단계 포함 |
|---|------|:---:|
| 1 | **신청** — 사용자가 앱에서 "파트너 신청" → `pending` | ✅ |
| 2 | **승인 화면** — 관리자가 pending 목록 확인 → 승인/거절 | ✅ |
| 3 | **게이트** — 승인 화면은 admin만 접근 (Clerk role) | ✅ |
| 4 | 결제 연동(insider 자동과금) | ❌ 별도(payments 트랙) |
| 5 | 파트너 전용 대시보드 콘텐츠 확장 | ❌ 승인되면 기존 insider 게이팅이 이미 처리 |

## 3. 설계 결정 (확정) — B2B SaaS 관행 대조 완료 ✅

> 아래 3가지는 웹 리서치로 **주류 B2B SaaS 관행에 부합함을 검증**했다(출처 §12).

| 결정 | 선택 | 판정 |
|------|------|------|
| **저장** | **Prisma DB = entitlement 단일 진실** + Clerk metadata = 파생 캐시 | ✅ 표준 |
| **admin 게이트** | Clerk `publicMetadata.role="admin"` 수동 부여(운영자 소수) | ✅ 초기 적정 |
| **신청 사유** | 선택(optional) + placeholder 가이드 문구 | ✅ 표준 |

### ⚠️ 핵심 정정 — "DB가 단일 진실, Clerk는 캐시"
당초 "DB=신청 진실 / Clerk=권한 진실" 2원장으로 잡았으나, 리서치 결론은 반대다:
- **DB(`PartnerApplication` + `User.plan` 성격)가 entitlement의 단일 진실.**
- Clerk `publicMetadata.plan`은 **빠른 게이팅용 파생 캐시.** 토큰 클레임은 세션 갱신 전까지 stale하므로 권한의 "진실"로 삼으면 안 됨.
- **insider 접근을 실제로 여는 서버 게이팅은 최종적으로 DB를 확인**(또는 갱신된 클레임). Clerk metadata만 믿지 않는다.

### 저장 스키마 (Prisma — `packages/database/prisma/schema.prisma`)
```prisma
model PartnerApplication {
  id         String                  @id @default(uuid())
  userId     String                  // Clerk user_id (== User.id)
  status     PartnerApplicationStatus @default(pending)
  reason     String?                 // 선택. 신청 사유
  decidedBy  String?                 // 처리한 admin Clerk user_id
  decidedAt  DateTime?
  note       String?                 // 거절 사유 등 관리자 메모
  createdAt  DateTime                @default(now())
  updatedAt  DateTime                @updatedAt

  @@index([status])
  @@index([userId])
}

enum PartnerApplicationStatus {
  pending
  approved
  rejected
}
```
- 기존 `User`/`Organization` 모델에 이미 `plan` 필드 있음 → **승인 시 DB의 plan도 `insider`로 갱신**(단일 진실), 그다음 Clerk 캐시 push.
- `plan.ts`에는 라벨/게이팅 로직만 유지(변경 최소). `PartnerStatus` 표기 타입만 추가.

## 4. 승인 = 재동기화 가능한 2단계 write (드리프트 방지)
```
[승인 액션] (admin 게이트 통과 후)
 1) DB 권위 write   : PartnerApplication.status=approved, decidedBy/At  +  User.plan=insider   (한 트랜잭션)
 2) Clerk 캐시 push : updateUserMetadata({ plan:"insider" })  ← 멱등·재시도
     └ 실패해도 DB는 approved 유지 → 다음 로그인/재동기화 잡에서 재push (approved인데 캐시 free면 교정)
```
- **DB 커밋 후 Clerk fire-and-forget 금지.** Clerk write가 실패하면 승인 유저가 캐시상 free로 갇힘 → 재동기화 경로 필수.
- 승인 직후 사용자가 바로 반영 보게 하려면 세션/클레임 refresh 유도 또는 서버 재확인.

## 5. 상태 전이
```
none ──(사용자 신청)──▶ pending ──(admin 승인)──▶ approved  [DB.plan=insider → Clerk 캐시]
                          │
                          └──(admin 거절)──▶ rejected ──(사용자 재신청)──▶ pending
```
- 이미 `insider`/`pro`/`enterprise`인 유저는 신청 버튼 숨김(이미 접근권 있음).
- `PartnerApplication`은 유저당 1건(최신)로 유지하거나, 재신청 시 새 row + 최신만 조회. → 이력 보존이 DB안의 장점.

## 6. 화면 / UX (⭐ UI/UX = 핵심 요소)

> B2B 승인 플로우의 UX 원칙: **상태를 항상 명확히 보여준다**(신청 전/심사 중/승인/거절이 한눈에), **막다른 길을 안 만든다**(거절엔 사유+다음 행동), **관리자는 빠른 처리**(목록→원클릭 결정→낙관적 반영).

### 6-A. 사용자 측 — 상태별 단일 컴포넌트 `PartnerCTA`
진입점 = 대시보드(`UpgradeLadder` 인근) + 사이드바. **상태 하나당 화면 하나**로 분기:

| 상태 | 표시 | 행동 |
|------|------|------|
| `none` (free, 신청 전) | "파트너로 신청하기" 카드 + 혜택 1~2줄 | [신청] → 모달(사유 optional, placeholder="예: 대행사로 클라이언트 GEO 진단에 활용") |
| `pending` | "심사 중" 배지 + 신청일 + "보통 N일 내 검토" 안내 | 버튼 없음(중복신청 차단). 취소는 범위 밖 |
| `approved` | 노출 안 함(이미 insider → 기존 게이팅이 콘텐츠 오픈) | — |
| `rejected` | 거절 안내 + **관리자 메모(사유)** 표시 | [다시 신청] → 모달 재열기 |

- 신청 모달: 사유는 **선택**, 빈칸 제출 허용. 제출 후 즉시 `pending` UI로 낙관적 전환 + 토스트("신청 접수됐어요").
- 접근성: 배지에 색만 쓰지 말고 텍스트 라벨 동반, 버튼 로딩/disabled 상태 처리(소셜 로그인서 쓰던 ready 가드 패턴).
- 서버 액션: `apps/app/app/actions/partner/apply.ts` (`"use server"`, self만, 이미 pending/approved면 무시).

### 6-B. 관리자 측 — `/admin/partners` 검토 화면 (admin만)
- 라우트: `apps/app/app/(authenticated)/admin/partners/page.tsx` (신규, 서버 컴포넌트).
- 레이아웃: **pending 우선** 목록(신청일 asc) + 상단 상태 필터 탭(대기/승인/거절). 디자인시스템 테이블·배지 재사용.
- 행(row): 이름·이메일·사유(없으면 "사유 미입력" 회색)·신청일 + [승인] [거절] 버튼. 거절은 사유 입력 인라인(선택).
- 인터랙션: 결정 시 **낙관적 업데이트**(행이 즉시 처리됨으로 이동) + 실패 시 롤백 토스트. 빈 목록엔 "대기 중인 신청이 없어요" empty state.
- 서버 액션: `apps/app/app/actions/partner/decide.ts` — **admin 게이트 필수**(§7) + §4의 2단계 write.

## 7. 관리자 게이트 (admin role) — **확정: role metadata**
- **Clerk `publicMetadata.role="admin"`** 을 운영자 소수 userId에 수동 부여(1회 설정).
- `packages/auth`에 서버 헬퍼 `isAdmin()` 추가. `/admin/*` 라우트 + `decide.ts` 첫 줄에서 재확인, 아니면 throw/404. **클라이언트 클레임만 믿지 않음**(서버 재확인).
- ⚠️ 관행 주의: 이 `admin`은 **플랫폼 운영자 권한** — 고객 org role과 **네임스페이스 분리**(org membership role과 섞지 않는다). 운영자↑·권한 세분화 필요해지면 그때 RBAC로 승격.
- ⚠️ 실행백로그 D14 P1 `[Clerk admin role 설정여부 확인필요]`를 이 결정으로 해소 → 백로그 갱신.

## 8. 구현 순서 (다음 세션 실작업)
1. **DB** — `schema.prisma`에 `PartnerApplication` 모델 + enum 추가 → `prisma generate` + 마이그레이션.
2. `packages/auth`에 admin 판정 서버 헬퍼(`isAdmin()`, `role==="admin"`) + `plan.ts`에 `PartnerStatus` 표기 타입.
3. `actions/partner/apply.ts` — 신청(self, DB에 pending row 생성, 사유 optional).
4. `actions/partner/decide.ts` — 승인/거절(admin 게이트 → §4 2단계 write: DB 권위 + Clerk 캐시 push·재시도).
5. `(authenticated)/admin/partners/page.tsx` — 관리자 검토 UI(§6-B, 디자인시스템 재사용).
6. 사용자 측 `PartnerCTA` — 상태별 분기(§6-A) + 신청 모달, `UpgradeLadder`/사이드바 연결.
7. insider 게이팅 서버 확인이 DB 기준인지 점검(캐시 stale 대비).
8. 검증: `apps/app`에서 `npx tsc --noEmit` 0 · `npx ultracite fix` · 배포 후 크롬 라이브(신청→승인→반영 E2E).
9. 실행백로그 D14 P1(admin role) 상태 갱신.

- 승인/거절 시 사용자 **알림**(메일/앱내) — `packages/notifications` 존재. 이번 범위 밖, 승인 UX 붙은 뒤 추가 권장.
- 결제 연동(insider 자동 과금) — payments 트랙.

## 11. 리스크 / 주의
- **캐시 드리프트**: DB approved인데 Clerk free → §4 재동기화 경로 필수. insider 게이팅은 DB 확인이 최종.
- **admin 오부여**: role=admin은 강력. 부여 대상 userId 소수·기록.
- **낙관적 UI 롤백**: 승인/신청 낙관적 반영이 서버 실패 시 되돌려야 함(토스트).

## 12. 출처 (B2B SaaS 관행 검증, 2026-07-28 웹 리서치)
- entitlement 단일 진실은 앱 DB, auth provider는 미러/캐시: Stigg, nhimg, Clerk webhooks 문서, Tim Koch(Medium)
- 내부 admin role은 초기 metadata-role 허용·단 org role과 분리: Descope RBAC, WorkOS(B2B user management)
- 게이트/웨이트리스트 사유 필드는 optional 기본·심사에서 자격 확인: Unicorn Platform, Waitlister
