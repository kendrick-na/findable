## 1. 냉정한 현 진단 — 반복 마찰의 근본 4개 (+공통 조상)

**뿌리 1 — 신원의 진실이 셋으로 쪼개졌고 아무도 정합을 강제 안 함.** Clerk(세션·멤버십)·Prisma/Neon(Brand·Tracking)·AuditJob.email(익명진단) 세 축이 따로. 잇는 유일한 정공 다리(Clerk 웹훅)가 죽어서 같은 일(org를 DB에) 하는 폴백이 3벌 공존(web lazy·app ensure-org·죽은 webhook). → **재발한다.** 결제 웹훅·파트너승인·plan 게이팅이 전부 "Clerk+DB 2단계 write"라 소유자 안 박으면 기능마다 "한쪽만 써짐" 버그 반복.

**뿌리 2 — org/user 소유 경로가 배포 안 되는 앱(apps/api)에 산다 (진짜 근본).** 웹훅이 이미 user/org upsert를 구현했으나 (a) apps/api Vercel 미링크·미배포, (b) `CLERK_WEBHOOK_SECRET=""` 빈값 → **두 겹으로 죽음.** Clerk가 이벤트 보낼 대상이 없어 코드가 있어도 실행 0회. → 1회성 배치 실수(재발 아님), 단 방치하면 상시 데이터 부채.

**뿌리 3 — 잡 오케스트레이터(runner)가 web에 갇혀 app이 브라우저로 경계 넘음.** ※재정의: 진짜 측정 엔진(queryAllEngines·crew·brand-identity)은 이미 `@repo/ai`에 **올바르게** 있음. 갇힌 건 오케스트레이션 껍데기(runner.ts=프롬프트→엔진→집계→AuditJob→PDF→Tracking)뿐. 이게 web 내부 경로(`@/env`·`@/lib/*`)에 묶여, app "추적 시작"이 **브라우저 크로스 서브도메인 fetch로 www를 때림**. 이 한 줄이 CORS·크로스쿠키·오리진정합·Clerk설정 의존을 전부 파생. → 조건부 재발(대시보드가 www 결과를 더 당길수록 확대).

**뿌리 4 — relationMode="prisma"가 "조용한 손상"을 기본값으로.** Neon이 FK 강제 안 해 Org 없이 Brand 만들어도 차단 아니라 고아 row가 에러 없이 성공. ensure-org로 방어 중이나 = **개발자가 매번 기억해야 함**(ensureBrand D4 주석이 "완전 원자성 없음" 자백). → 재발한다.

**공통 조상 — "제약을 강제하는 주체가 시스템이 아니라 사람(개발자 기억)."** 신원정합=웹훅이 강제해야 하는데 폴백3벌. env정합=검증이 해야 하는데 z.url()이 형식만 보고 값(`app.`)은 사람이. 경계통과=프레임워크가 흡수해야 하는데 라우트마다 CORS 수작업. 참조무결성=DB가 해야 하는데 ensureX. **그래서 "tsc/build 통과, 라이브에서만 터짐"이 반복** — 이 4계층은 전부 컴파일타임에 증명 불가한 런타임 계약(env 값·배포 앱 집합·DB 실제 제약·쿠키 스코프)이라 타입시스템이 원리적으로 못 봄.

## 2. 대중 표준 대비 갭

**잘 맞는 것 (바꾸지 마라):**
- 도메인 분리(www 마케팅 / app 제품) = SaaS 정설. 문제 원인 아님.
- 엔진을 www에 둔 결정도 합리(무료진단=마케팅 CTA, SEO·전환상 www).
- `@repo/ai` 엔진 배치, 웹훅 apps/api 배치 = next-forge 표준 부합.

**벗어난 것 (진짜 갭 2개):**
- **갭 A — Clerk 크로스오리진을 "satellite"로 오해.** Clerk은 **같은 상위도메인 subdomain끼리 세션 기본 공유**. www·app 둘 다 `*.findable.co.kr`이라 satellite **없이** 세션이 흐름. satellite는 최상위 도메인이 다를 때만. → 버튼의 "401이면 satellite" 주석은 오진. 진짜는 3값 정합: (a)Clerk allowed origins에 두 subdomain, (b)쿠키도메인 `.findable.co.kr`, (c)`NEXT_PUBLIC_APP_URL`이 `https://app.findable.co.kr`(반드시 `app.`). `[확인필요: Clerk 대시보드 실값]`
- **갭 B — 모노레포인데 앱 간 통신을 HTTP로.** next-forge의 존재 이유가 `packages/*` 공유인데 runner가 web에 갇혀 app이 www를 HTTP로 부름. 표준 SaaS는 앱이 자기 도메인 API를 부름(크로스오리진 인증 호출 안 함). 모노레포 이점 버린 상태.

**게이팅 시장 표준:** GEO 카테고리 지배 관행 = **가입 없는 즉시 진단**(no-signup). 상위 유료만 게이팅. 반면 전환 데이터는 freemium(가입 후 무료) 12% vs free-trial 3~4%, reverse trial 7~21%로 "가입 후"가 우월. → 두 표준 충돌 → **하이브리드가 정답**(P4).

## 3. 권고 로드맵 (우선순위)

### P1 — 웹훅을 배포되는 앱으로 이설 + 신원 소유자 1개로 못 박기 (뿌리1+2)
- **무엇**: 죽은 apps/api 웹훅 대신 **웹훅 라우트를 이미 배포된 app으로 이설**(app은 Clerk·database 의존 이미 보유) + `CLERK_WEBHOOK_SECRET` 채움 + Clerk 구독. org/user 소유를 **웹훅 하나로 확정**, ensure-org는 폴백으로 강등.
- **왜**: org 0행/AuditJob 54행 직접 원인 제거. 폴백 3벌 병존이 최악, 안 풀면 결제·파트너승인에서 같은 버그 재생산.
- **위험**: 낮음(멱등 upsert). app 이설=인프라 0 추가(api 신설보다 실용적). `[확인필요: api 살리기 vs app 이설]`

### P2 — runner를 `@repo/audit` 공유 패키지로 승격 (뿌리3·갭B) ★가장 큰 레버
- **무엇**: `apps/web/lib/audit/{runner,crew-runner,briefing-runner,tracking}.ts`의 `@/env`·`@/lib/*` 의존을 인자·주입으로 끊고 패키지화. PDF(puppeteer·@vercel/og)는 무거우니 분리 검토.
- **왜**: app이 서버에서 runner 직접 import → **www HTTP 호출 자체가 사라짐 → CORS·크로스쿠키·오리진·satellite 의존이 원인째 소멸.** 증상 5개 중 3개가 이 하나로 사라짐. 모노레포를 제대로 쓰는 것.
- **위험**: 중(env·경로 의존 해체 손감, server-only·puppeteer 번들 경계, AI Gateway 키 노출 범위). runner가 순수함수라 로직 위험 낮음.
- **(a) 문항 답**: **공용화가 게이팅 전환보다 우선.** 게이팅은 데이터 축 정리하나 경계(CORS)를 안 없앰. 공용화는 경계 자체를 없앰. 배타 아니라 **P2가 P4의 토대.**

### P3 — 로그인/인증 안정화, 재발 끊기 (뿌리2·갭A)
- **무엇**: satellite 가정 폐기, same-parent-subdomain 세션공유로 재검증. Clerk 대시보드 allowed origins(두 subdomain)·쿠키도메인(`.findable.co.kr`)·`NEXT_PUBLIC_APP_URL`(`app.` 포함) **3값만 정합**. 표준 `<SignIn/>` 유지(지난 근본해결 존중, 커스텀 useSignIn 재생성 금지).
- **왜**: "3주 로그인"이 재발하는 건 매번 라이브 실측으로 fix 찾아서. 근본은 3개 런타임 값 정합이지 컴포넌트 아님. P2 후엔 app이 www 안 부르므로 크로스오리진 인증 표면 대폭 축소.
- **위험**: 낮음(설정값, 코드 아님). `[확인필요: Clerk 대시보드 3값]`

### P4 — 무료 audit 게이팅: 하이브리드 (사용자 아이디어 냉정 평가)
- **(b) 평가**: "무료도 가입 강제 + 바로 대시보드"는 **부분 채택, 전면 게이팅은 자충수.** 아키텍처론 신원축 분리(뿌리1)를 정면 해소하는 강수지만, GEO 시장표준(no-signup)을 거스르고 최상단 깔때기 전환 급락. 유료 지불의사 미검증 단계엔 리드풀을 좁히는 게 아니라 넓히며 질을 태그해야.
- **무엇(하이브리드=표준답)**:
  1. **문 앞(www)**: 진단 실행=무게이트 유지. 결과 시 email-first(현 AuditJob.email 강화). PDF 제공.
  2. **문 안(app)**: "저장·매주 추적하려면 무료 계정(소셜 30초)". 가입을 무료차단 아니라 **결과 소유·추적의 대가**로. aha moment 직후 최고 전환 순간.
  3. **reverse trial**: 가입 시 growth 기능 14일 전개→종료 후 free 강등. `trialEndsAt`·`billingStatus=trialing` 이미 대응.
  4. **backfill 다리**: email 고아 AuditJob을 가입 시 org에 이어붙임. "지난주 익명으로 본 진단, 가입하면 대시보드로"=전환 후킹.
- **함정**: 게이팅은 "미래 신규 데이터"만 깨끗하게 함. **원인 둘(P1 웹훅, P2 결과 org 적재)을 게이팅이 대신 안 해줌.** 게이팅을 P1·P2보다 먼저 하면 "가입자는 있는데 데이터는 여전히 고아"인 최악. AuditJob엔 org/User FK 없어, 로그인 유저가 진단해도 결과는 여전히 AuditJob(email키)에 떨어짐 — 이 연결 코드가 진짜 작업이지 게이팅이 아님.

## 4. 지금 20번을 이 큰 그림에서 어떻게 마무리?
- **핵심 통찰**: 지금 CORS 급한불(NEXT_PUBLIC_APP_URL `app.` 누락)을 끄는 건 **P2를 하면 원인째 사라질 문제에 임시 반창고.** 지금 CORS를 완벽히 고쳐도 P2에서 다 버릴 코드.
- **권고**: 20번 목표(=org 시계열 데이터 토대, P5)는 유효·값짐. 단 **트리거 경로(app→www fetch, 엄격판 A)는 P2로 갈아탈 임시물로 간주.** 지금은 (1)P1 웹훅 살리기 + (2)env 3값 정합(P3)로 **로그인·CORS를 "설정으로" 끝내고**, 트리거 코드 자체는 P2 때 app 내부 직접호출로 대체. → 지금 CORS에 시간 더 쓰지 말고 env 정합만.
