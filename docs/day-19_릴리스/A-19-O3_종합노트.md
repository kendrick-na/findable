# A-19-O3 — 종합 노트 (프로덕션 릴리스·릴리스 노트)

> Day19 (2026-07-29, 사전작성) · Findable · 4주차 프로덕션

## 오늘 한 일
Findable의 실제 git·배포 상태를 릴리스 관점으로 블라인드 재검증. 배포 자동화(Vercel)는 있지만 **릴리스 관리(무엇을·언제 내보내고 기록하나)가 통째로 비어 있음**을 확인.

## ★ 핵심 발견 4건 (→ A-19-O1)
- **D19-1** 프로덕션(main) vs 개발분 격차 큼: feature가 **13커밋 앞 + 미커밋 111파일**. 릴리스가 밀려 배치가 비대(문제 추적·롤백 어려움). Day15 실습발 commit(2ce7f1b)도 아직 프로덕션에 없음.
- **D19-2** 릴리스 노트/CHANGELOG **0건**. 변경 기록=커밋 메시지뿐(개발자용). 단 컨벤셔널 커밋 규율 우수→노트 자동생성 재료는 됨.
- **D19-3** 미커밋 111개(untracked 50=Day17 sweep 이중구현·digest cron / modified 61=홈·audit·Day18 legal). 유실·뒤섞임·미정리분 딸려나갈 위험 3중.
- **D19-4** 롤백(Vercel Instant Rollback) 가능하나 릴리스 기록 없어 "뭘 되돌리는지" 판단 근거 약함. 노트↔롤백은 한 쌍.

## 핵심 교훈 3가지
1. **배포 자동화 ≠ 릴리스 관리.** push하면 배포되는 것과, 무엇을 언제 내보낼지 결정·기록하는 것은 다른 문제. Findable은 앞은 있고 뒤가 없다.
2. **릴리스가 밀리면 배치가 비대해지고, 비대한 배치는 되돌릴 수 없다.** 작게 자주 릴리스해야 문제를 격리한다. 13커밋+111파일을 한 번에 = 문제 시 원인 미궁.
3. **릴리스 노트는 롤백의 지도다.** 무엇을 내보냈는지 기록이 없으면, 장애 때 무엇을 되돌릴지도 모른다. Day18 런북(대응)·Day17 알림(감지)과 함께 "감지→기록→대응"의 마지막 조각.
